# 계획 워크플로

이 skill은 루트 `CLAUDE.md`의 계획 전용 경계를 따른다. Plan Mode에서 파일 편집이 제한되면 사용자에게 문서 작성이 가능한 권한 모드로 전환하도록 안내한다. 사용자 승인 없이 프로젝트 파일·코드는 수정하지 않는다.

## 공통 규칙

- 처음에는 `docs/.status`가 존재하는지 확인한다. 없으면 0단계 초안부터 시작한다. 승인된 선행 문서와 현재 단계 문서만 관련 범위에서 읽고, 사용자가 제공한 기존 업무정의서 등 입력 자료도 확인한다.
- 한 번에 현재 단계의 초안만 작성한다. 사용자가 명시적으로 승인한 후에만 다음 단계로 이동한다. 질문은 한 번에 최대 5개만 한다.
- 사실은 `사용자 확인`, `외부 공식 자료 확인`, `임시 가정`, `미확인`으로 구분한다. 자료 출처·확인일과 가정의 근거·영향·확인 주체·검증 방법을 기록한다. 설계 결정을 바꿀 보안·권한·데이터 의미·연계·환경 질문은 `차단`으로 표시하고 해결 전에는 해당 게이트 승인 요청을 하지 않는다.
- 각 문서는 상태(`draft`/`approved`), 결정·근거·대안, 미해결 질문과 다음 행동을 포함한다. 승인된 결정 변경 시 영향받는 요구사항(R-ID), 설계(D-ID), 작업(T-ID)을 제시하고 필요한 단계부터 재승인받는다.
- 사용자가 승인한 입력 자료가 어떤 단계의 내용을 이미 담고 있으면 새로 조사하지 않고 해당 단계 문서로 옮긴다. 출처(파일명·버전·절)를 적고 기존 ID(R-ID 등)와 표기(`[제안]`, 미확인)를 유지한다. 그 단계의 품질 기준에 비춰 빠진 항목만 보완 목록과 질문으로 제시한다. 입력 자료의 승인은 참고 근거일 뿐이므로 `docs/` 단계 문서는 사용자가 다시 명시 승인해야 `approved`가 된다.
- 아래 검증 항목 중 해당하지 않는 내용은 이유와 함께 `해당 없음`으로 처리한다. 문서 양을 늘리기 위해 수치나 사내 제약을 만들어내지 않는다.

## 0. 착수 (`docs/00-context.md`)

대상 업무·사용자·이해관계자, 현행 절차와 병목·증거, 입력·출력·데이터 민감도, 목표·범위·기한·가용 자원을 조사한다. OS/언어/DB 버전, 사내망·외부 API·AI 허용 여부, 사내 표준·권한·승인 절차를 확인한다. 미제공 수치는 미확인과 확인 방법으로 남긴다.

출력: 사실/가정/질문 목록, 현재와 목표 업무의 차이, 계획 범위. 게이트 `context:approved`: 사용자가 문제와 범위를 확인하고 요구사항을 왜곡할 차단 질문이 없다.

## 1. 요구사항 (`docs/01-requirements.md`)

기능별 R-ID와 사용자·조건·입력·기대 출력·오류 상황·관찰 가능한 인수 기준을 적는다. MVP와 후순위, 범위 밖, 사람의 최종 판단 영역을 구분한다. 해당하는 비기능 요구사항은 처리량·지연·정합성·보안·감사·보관·가용성·복구·모니터링·배포/롤백으로 나누되 근거 없는 목표 수치를 확정하지 않는다. 성공 기준의 측정 방법·기준선·판정 주체를 기록한다.

게이트 `requirements:approved`: 사용자가 범위·우선순위·인수 기준을 확인했고 핵심 시나리오·예외 동작을 검증할 수 있다.

## 2. 설계 (`docs/02-design.md`)

- 범용 데이터 모델: 엔티티·관계·속성·키·제약·이력·변경/삭제·데이터량·보관·인덱스 후보. 사용자가 확인하지 않은 기존 테이블은 확정 구조처럼 적지 않는다. 특정 시연 시나리오에 스키마를 종속시키지 않는다.
- 검증: 성격이 다른 업무/조직의 대표 사례 최소 2개와 변경·누락·중복 등의 예외 사례를 가상/마스킹 레코드 및 입출력 흐름에 적용한다. 해결되지 않은 사례는 모델 수정 또는 지원 범위 제외로 기록한다.
- 인터페이스: 해당하는 API·CLI·화면·파일 계약, 필수값·오류 응답·중복/재시도·연계 책임 경계.
- 결정: 현실적인 대안 2~3개의 호환성·사내 표준·보안·운영/유지보수·비용 비교. 대안이 하나뿐이면 근거를 쓴다. 주요 결정별 D-ID, 선택 이유·포기한 대안·미검증 전제·검증 방법을 남긴다.
- 보안/운영: 권한, 민감정보, 로그 포함/제외, 장애 감지·복구·배포·롤백. AI 사용 시에만 AI 역할·입출력·오답 처리·인간 검토·평가 데이터를 설계한다.
- 모든 핵심 R-ID에 대응하는 D-ID를 추적표로 연결한다.

게이트 `design:approved`: 대표·예외 사례에 핵심 모델/인터페이스를 적용해 봤고, 구현 가능성을 바꾸는 호환성·보안·권한 질문이 해결되거나 범위에서 제외됐다.

## 3. 실행 계획 (`docs/03-plan.md`)

제안 디렉터리 구조·설정·실행·테스트·린트·배포/롤백 방법을 문서로만 제시한다. 각 T-ID에 연결 R-ID/D-ID, 선행 조건, 외부 의존성, 확인 주체, 산출물, 정상/오류 검증 방법과 완료 기준을 적는다. 첫 작업은 가장 작은 입력 → 처리 → 출력 흐름으로 한다. 기한·가용 인력을 확인한 경우에만 일정/소요를 추정하며, 근거가 약하면 범위와 마일스톤만 제안한다. 위험별 발생 조건·영향·대응·계획 재검토 조건을 적는다. 구현 전 권한·승인·마스킹된 데이터 준비 상태를 명시한다.

게이트 `plan:approved`: 사용자가 작업 순서·검증 방법·범위와 준비물을 확인한다.

## 최종 착수 준비성 점검

1. 모든 핵심 R-ID가 인수 기준·D-ID·T-ID에 연결되는가?
2. 서로 다른 대표 사례 및 변경·누락·중복 등의 예외에 핵심 모델이 성립하는가?
3. 주요 기술·연계 결정에 근거와 실제 환경 검증 방법이 있는가?
4. 권한·보안·데이터 확보·외부 승인·담당자 중 구현 착수 차단 조건이 남았는가?
5. 작업마다 정상/오류 검증 방법과 완료 기준이 있고, 주요 위험에 대응/재계획 조건이 있는가?

차단 조건이 있으면 `planning:complete`를 기록하지 않는다. 확인 주체·증거·다음 행동을 남긴다. 비차단 가정은 사용자가 인지하고 승인한 경우에만 남길 수 있다. 점검 통과 후 `docs/.status`에 `planning:complete`를 기록하고 확정 결정 3~5개, 남은 비차단 가정, 첫 구현 작업과 별도 구현 세션 시작 프롬프트를 요약한다. 구현은 하지 않는다.

## 상태 파일 (`docs/.status`)

현재 단계, 문서별 `draft`/`approved`, 승인 게이트·대상 문서·사용자 승인 표현·확인 가능한 시각/시간대·조건, 차단 질문, 최종 점검 결과, 다음 세션 첫 행동을 적는다. 사용자가 명시 승인하지 않은 문서는 `approved`로 기록하지 않는다. 시각을 알 수 없으면 임의로 채우지 않는다.
