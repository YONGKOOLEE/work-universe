### 유니버스 개념 (사용자 재설명, 2026-09-30)

정의서 v0.2 §1을 사용자가 다시 설명했다. 이 절은 그 설명을 이해한 대로 정리한 것이며, 사용자 확인 대기 중이다.

1. **업무 중심 컨테이너:** 어떤 단위의 업무든 그 업무의 고유 유니버스를 만들고, 노드는 그 유니버스 안에서 생긴다. 유니버스가 조직이 아니라 업무에 붙기 때문에, 조직개편으로 소속이 바뀌어도 그 업무의 이력은 끊기지 않는다. 소속 변경은 컨테이너를 바꾸는 일이 아니라 유니버스 안에 기록되는 사실이다.
2. **사람·조직 이력의 연속성:** 사람과 조직을 관리하는 일은 조직관리팀의 업무다. 따라서 사람과 조직은 **조직관리팀 업무 유니버스 안의 노드나 트리**로 존재한다. 조직관리팀이 계속 입력하므로 인물 이력도 끊기지 않는다.
3. **틀은 하나:** 조직관리 유니버스도 특별한 종류가 아니라 같은 틀의 유니버스 하나다. 이는 v0.2 §12-2(일반 유니버스, A 수준)와 같다.
4. **꼭지를 모아 상위 단위 구성:** 업무 → 팀 → 부서 → 본부 → 회사. 하위 유니버스의 꼭지(최상위 노드)를 모아 더 큰 단위의 유니버스를 만들 수 있어야 한다. 예를 들어 A·B·C팀 유니버스를 통합해 부서 유니버스를 새로 그린다(R-11).
5. **목표:** 특정 업무·조직에 종속되지 않고 어디에나 통하는 "업무 유니버스" 틀과 도구를 만든다(R-07).

2단계 데이터 모델에서 가상 사례로 검증할 질문(비차단):
- 팀 유니버스는 여러 업무 유니버스의 꼭지를 모은 것인가, 팀이 직접 만든 유니버스 하나인가? 두 경우 모두 같은 틀로 표현되어야 한다.
- 업무 유니버스 안의 "사람" 노드와 조직관리 유니버스의 "사람" 노드는 사번으로만 대응시킨다. 조직관리 유니버스의 기준 데이터 검증 역할은 v0.2에 따라 R-09 문서로만 다룬다.

## 3. 입력·출력·데이터 민감도

- 입력: 가상 데이터만 사용한다. 사내망·보안 제약 때문이다. [사용자 확인, §10, R-06]
- 출력: 탐색 화면, 인수인계 초안, 인사이트, 통합(부서) 유니버스를 만든다. 제출물은 실행 가능한 산출물, 시연 영상, 소개자료 1~2쪽이다. [사용자 확인, §5]
- 민감도:
  - 실사용 시 인사·조직 데이터(사번, 소속, 담당 이력)는 민감정보다. 근거는 정의서 v0.1 §10이다. v0.2는 이 내용을 R-09 문서 범위로 넘겼다.
  - 프로토타입에서는 실제 사람·업무·사내 정보를 넣지 않는다. 사번도 가상 형식을 쓴다. [임시 가정: 가상 사번 형식이 실제 사번 체계와 닮지 않아야 함. 확인 주체: 사용자]

| 조직 조망 | 수단 없음 | 팀 유니버스를 통합해 부서 단위 인사이트 제공, 해석은 사람이 함 (R-11, R-05) |

## 7. 계획 범위

- 대상: 공모전 프로토타입(가상 데이터)과 실사용 전환 경로 문서(R-09). 출처는 정의서 v0.2 §5다.
- MVP 종단 흐름: 가상 데이터 탐색 → 자료 1건 추가 → 업무 유니버스에서 인수인계 초안 생성 → 인사이트 1건 확인.
- 제외 항목:
  - 실제 사내 시스템·데이터 연동
  - 조직관리 유니버스의 기준 데이터 검증 역할(R-09 문서로만 다룸)
  - 효과 수치의 확정
  - 의사결정 자동화
- 사람의 최종 판단 지점:
  - 인수인계 문서 확정
  - 인사이트 해석과 인력배치
  - 서로 다른 유니버스 간 업무 동일성 연결(자동 병합 금지)
- 요구사항 R-01~R-13은 1단계에서 정의서 v0.2 §7을 옮겨 ID와 표기를 유지한 채 보완한다.
