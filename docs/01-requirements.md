## 3. 범위 구분

- **범위 밖** (v0.2 §5 유지):
  - 실제 사내 시스템·데이터 연동
  - 조직관리 유니버스의 기준 데이터 검증 역할(R-09 문서로만 다룸)
  - 효과 수치의 확정
  - 인력배치 등 의사결정 자동화
  - 모바일 앱(00-context, 2026-09-30)
- **사람의 최종 판단 영역** (v0.2 §6):
  - 인수인계 문서 확정(R-03)
  - 인사이트 해석·활용과 인력배치(R-05)
  - 서로 다른 유니버스 간 업무 동일성 연결(R-11)
- **LLM의 역할** [사용자 확인 "전부다", 2026-09-30]: LLM은 위 판단을 대신하지 않고, 근거 노드에 기반한 문장 작성과 후보 제시만 한다.
  - (a) 인수인계 초안 문장화(R-03)
  - (b) 인사이트 결과의 자연어 설명(R-05)
  - (c) 업무 동일성 후보 제시(R-11)
  - 세 역할 모두 LLM이 없으면 규칙 기반으로 대체된다(R-04의 원칙을 확장).
  - 계산 자체(밀집/공백 집계, 유사도 등)는 LLM 없이 그래프 통계로 한다.
- **LLM 연결 방식** [사용자 결정 "2번으로 진행", 2026-09-30]:
  - 용어: 이 문서의 "외부 API"는 **Claude API**를 뜻한다. 사내 LLM과 구분하려고 "외부"라고 불렀다.
  - 개발 PC와 시연 영상 촬영에서는 **Claude API 키**로 (a)(b)(c)를 LLM으로 동작시킨다.
  - 제출물에는 키를 넣지 않는다(A-2). 그래서 심사위원 PC에서는 **규칙 기반**으로 동작한다(R-04).
  - 사내 LLM은 사용 방법이 정해지면 같은 연결부(R-15)에 설정만 바꿔 연결한다(P2).
  - API 키는 개발자가 Console에서 발급하고 선불 크레딧을 충전하는 것으로 가정한다. 비용 부담 주체는 **미확인**이다.
  - 연결부의 구체 설계(설정 방식, 키 보관, 호출 실패 처리)는 2단계에서 정한다.
  - **외부 공식 자료 확인**(Claude Help Center, 확인일 2026-09-30, https://support.claude.com/en/articles/9876003): 유료 Claude 구독(Pro, Max 등)에는 Claude API·Console 접근이 포함되지 않는다. API는 Console에서 별도로 가입하고, 선불 크레딧으로 과금된다(https://support.claude.com/en/articles/8977456). Claude Max 계정으로 프로그램이 Claude를 직접 호출하는 방식이 가능한지와 이용 조건은 **미확인**이다.
- **변경 CR-1** (사용자 승인 "cr-1 방식을 승인", 2026-09-30. 아래 RQ-5·R-15 내용보다 우선한다):
  - **기본 LLM 경로:** `사전 생성`이다. 개발 중 Claude Code(Claude Max)가 가상 데이터에 대한 (a)(b)(c) 결과를 미리 작성해 앱에 넣는다. API 비용은 0이다.
  - **표시:** 화면에 "사전 생성(개발 시 Claude로 작성)"으로 표시한다.
  - **새로 입력한 데이터(R-02):** 입력 기능은 그대로 구현한다. 규칙 기반 계산(초안 항목 채우기, 인사이트)도 새 데이터에 대해 그대로 동작한다. 사전 생성 결과가 없는 부분만 **LLM 문장 대신 규칙 기반 문장**으로 표시된다.
  - **실제 LLM:** 사용할 LLM(Claude API 또는 사내 LLM)이 확정되면 같은 연결부에 설정으로 넣을 수 있게 구현한다. Claude API 연결은 P2(선택)다.
  - **R-15 수정:**
    - 공급자는 `없음`, `사전 생성`, `Claude API`, `사내 LLM` 네 가지다.
    - AC ②: "사전 생성 또는 LLM 결과는 해당 방식으로 표시되고, 모든 문장의 근거 ID가 유효하다".
    - 우선순위: 연결부와 사전 생성은 P1, Claude API는 P2(선택), 사내 LLM은 P2.
- **변경 CR-3** (사용자 승인 "승인", 2026-10-01. 조건: 변환 규칙은 실제 데이터로 구현해 시각화한 뒤 확정):
  - **역할 (d) 업무정의서 → 유니버스 변환**을 추가한다. 업무 담당자가 쓴 업무정의서를 읽어 노드·연결·속성으로 구성한다.
  - **A(지금):** 개발 중 Claude Code가 업무정의서를 유니버스 JSON(02-design 12.2)으로 변환해 두고, 앱은 **JSON 가져오기 화면**으로 불러온다. CR-1의 사전 생성과 같은 방식이다.
  - **B(나중, P2):** 앱이 LLM 연결부(R-15)로 같은 JSON을 만든다. A와 B는 "JSON을 누가 만드느냐"만 다르고, 검증 → 미리 보기 → 사람이 가져오기 확정 과정은 같다.
  - AC: ① 변환 결과는 스키마 검증을 통과해야 가져올 수 있다. ② 모든 노드에 원문 근거(절 번호)가 있다. ③ 사람이 미리 보기를 확인하고 "가져오기"를 눌러야 저장된다. ④ 원문의 [가정]·[미확인] 표시가 보존된다.
  - 우선순위: A는 P1이며 범위 축소 대상에서 뺀다(사용자 결정 "웬만하면 빼지 않는 항목", 2026-10-01). B는 P2.
- **R-15** [1단계 제안]: LLM 연결부 교체 가능성.
  - 조건: 연결 설정 없음(심사위원 PC), 또는 Claude API 키 설정 있음(개발 PC, 영상 촬영).
  - 기대 출력:
    - 설정이 없으면 (a)(b)(c)가 규칙 기반으로 동작한다.
    - 키를 설정하면 Claude API로 동작한다. 기능 코드는 바꾸지 않는다.
    - 두 경우 모두 생성 방식이 표시된다.
  - 오류: 키가 잘못됐거나 호출이 실패하면 규칙 기반으로 전환하고 원인을 표시한다(R-04).
  - 인수 기준:
    - ① 키 없이 실행하면 (a)(b)(c)가 규칙 기반 결과와 함께 "규칙 기반"으로 표시된다.
    - ② 키를 설정하면 "LLM"으로 표시되고, LLM이 만든 문장에도 근거 노드가 연결된다.
    - ③ 제출물 파일에 키 문자열이 없다.
  - 우선순위: 연결부와 Claude API 연결은 **P1**이다. 영상 촬영 전에 완료해야 한다. 사내 LLM 연결은 **P2**다.

## 8. 위험 (이번 변경으로 생김)

- **K-1** (RQ-5 결정으로 대응됨, 2026-09-30):
  - 내용: 심사위원이 직접 실행하면 규칙 기반 결과만 보게 되어, 영상과 실행 결과가 다르게 보일 수 있다.
  - 대응:
    - 화면에 생성 방식(LLM/규칙)을 표시한다(R-15).
    - 실행 안내에 "키를 설정하면 LLM으로 동작한다"고 적는다.
  - 재검토 조건: 주최 측이 키가 들어간 제출물을 요구하거나 허용할 때.
- **K-2** (새 위험):
  - 내용: Claude API 비용 부담 주체가 **미확인**이고, 크레딧이 없으면 영상 촬영 전에 LLM 동작을 검증할 수 없다.
  - 대응: 크레딧 충전을 영상 촬영의 준비 조건으로 3단계에 넣는다.
  - 재검토 조건: 크레딧을 준비할 수 없으면 RQ-5의 대안 ①(외부 API 전면 생략)으로 되돌린다.
