## 1. 범용 데이터 모델 [2단계 제안]

### 1.1 설계 원칙

1. **유니버스는 업무에 붙는다**(00-context "유니버스 개념" 1). 소속과 조직은 유니버스 안의 사실(노드·연결·이벤트)이지 유니버스를 나누는 기준이 아니다.
2. **틀은 하나다**(R-07). 업무 성격별 필드를 스키마에 넣지 않는다. 업무 고유 정보는 노드의 자유 속성(키-값)과 태그로 담는다.
3. **바꾸지 않고 쌓는다.** 모든 변경은 이벤트로 남는다. 삭제는 숨김 표시만 한다(R-02 ②, R-14, R-05 흐름 변화). 예외: 연결·이력이 없는 실수 노드의 바로 삭제와 숨긴 뒤 「완전히 삭제」(자리표시)는 D-28(CR-13 D) (2026-10-23 검토9).
4. **통합은 원본을 건드리지 않는다**(R-11 ⑤). 상위 유니버스는 하위 유니버스의 꼭지를 참조한다.

|---|---|---|---|---|---|

### 1.3 핵심 노드 유형과 관계 유형

노드 유형(고정 6종):

| 유형 | 예 | 비고 |
|---|---|---|
| 꼭지 | 유니버스 자체 | 1.2 Root |
| 사람 | 담당자, 관계자 | 속성 `사번`(선택. 없으면 통합 때 확인 요청) |
| 업무 | 세부 업무, 절차, 과제 | 업무 유니버스의 하위 작업도 이 유형 |
| 산출물 | 문서, 링크, 보고서, 인수인계서 | 가상 제목과 요약만 저장 |
| 조직 | 팀, 부서 | 주로 조직관리 유니버스에서 트리로 사용 |
| 주제 | 키워드, 분류, 이슈 유형 | 유사 경험자와 반복 비효율 계산에 쓰는 공통 기준 |

관계 유형(고정 7종):

| 관계 | 의미 |
|---|---|
| 포함 | 꼭지 → 업무, 업무 → 하위 업무 |
| 수행 | 사람 → 업무. 유효 기간이 담당 기간이 됨 |
| 산출 | 업무 → 산출물 |
| 선후행 | 업무 → 업무 |
| 소속 | 사람 → 조직, 조직 → 조직. 유효 기간 있음 |
| 관련 | 꼭지 이외 모든 노드 → 주제 |
| 참조 | 꼭지 이외 노드 → 꼭지 이외 노드. 기타 연결 |

- 유형을 고정한 근거: 인사이트 계산(D-08)과 규칙 기반 초안(D-09)이 유형에 의존한다. 대신 업무별 고유 정보는 자유 속성과 태그로 담아 R-07을 지킨다.
- **개정안: 핵심 유형 + 하위 유형** [2단계 제안, 사용자 질문 "반드시 고정해야 하는지" 반영, 2026-09-30]
  - 사용자가 **하위 유형**을 자유롭게 추가할 수 있다. 예: 산출물 > 회의록·보고서, 사람 > 외부 협력사 담당자, 업무 > 점검·교육.
  - 하위 유형은 반드시 핵심 유형 하나에 속한다. 관계도 같은 방식이다. 예: 참조 > 검토함, 선후행 > 승인 후 진행.
  - 계산(D-08·D-09)은 핵심 유형으로 하고, 화면 표시·필터·범례는 하위 유형으로 한다.

| 대안 | 내용 | 판단 |
|---|---|---|
| ① 완전 고정 | 6개 노드 유형과 7개 관계 유형만 허용 | 계산은 가장 단순하지만, 업무 표현이 딱딱함 |
| **② 핵심 + 하위 유형 (권장)** | 계산용 핵심 유형은 고정하고, 표현용 하위 유형은 사용자가 추가 | 같은 틀(R-07)과 표현 자유를 함께 얻음. 비용은 편집 화면에 하위 유형 선택·추가 기능이 필요하다는 점(작은 기능) |
| ③ 완전 자유 | 유형을 사용자가 전부 정의 | 인사이트와 초안 규칙이 유니버스마다 달라져 R-07·R-05 조건을 지키기 어려움 → 포기 |

- **선택: ②** [사용자 선택, 2026-09-30. 조건: 나중에 확장할 수 있을 것]
- **확장 경로:**
  - **하위 유형 추가:** 데이터만 추가하면 된다. 코드 변경은 없다.
  - **핵심 유형 추가**(예: "고객", "시스템"): 유형 목록과 그 유형을 쓰는 계산 규칙(D-08·D-09)만 고치면 된다. 기존 데이터는 그대로 유지된다. 자주 쓰는 하위 유형을 핵심 유형으로 승격할 수도 있다.
  - **③(완전 자유)로 전환:** 가능하다. 다만 계산 규칙을 유형 대응표 기반으로 다시 짜야 한다.
- **확장을 위한 설계 조건:**
  - 핵심 유형 목록은 코드 한 곳(설정)에만 둔다.
  - 데이터에는 `핵심 유형`과 `하위 유형`을 따로 저장한다.
  - 모르는 유형의 데이터를 불러오면 오류로 멈추지 않고 "참조"·"기타"로 표시한다.

| 이벤트 | 기록 시점 | 쓰이는 곳 |
|---|---|---|
| 생성, 수정, 숨김 | 노드·연결을 만들거나 바꾸거나 숨길 때(자동 기록) | R-02 ②, 흐름 변화 |
| 담당 시작, 담당 종료 | 수행 연결이 생기거나 끝날 때 | R-03, 유사 경험자 |
| 인수인계 | 담당자가 교체될 때(보낸 사람, 받은 사람, 근거 산출물) | R-03, 반복 비효율 |
| 소속 변경 | 조직개편이나 발령 | R-14 |
| 메모 | 자유 기록(이슈, 결정 등) | R-03 근거, 흐름 변화 |

- **편집 되감기(CR-14 A, D-30):** 생성·수정(변경 전·후 값)·숨김·되살림과 연결·묶기·통합 판정 이벤트를 **기록 시각(`recorded_at`)의 역순으로 거꾸로 적용**해 과거 시점 문서를 만든다. 같은 기록 시각의 이벤트가 한 판이다. 「이 시점으로 되돌리기」는 지금 문서를 그 시점과 같게 만드는 명령을 한 묶음으로 적용하고(그 뒤 생긴 노드·연결은 숨김), 각 이벤트에 되돌림 메모를 남긴다. 사용자 이벤트(담당·인수인계·소속 변경·메모)는 되돌리지 않는다. 이벤트를 남기지 않는 「바로 삭제」·하위 유형 추가, 내용을 지운 「완전히 삭제」는 되감기의 한계다(limits).

### 1.5 이력·삭제·중복·누락 규칙

- **이력:** 노드·연결의 현재 값은 마지막 이벤트까지 반영한 상태다. 수정 전 값은 `수정` 이벤트의 "변경 전" 값으로 남는다(R-02 ②).
- **삭제:** 사용자 삭제는 `숨김`으로 처리한다. 숨긴 노드는 기본 화면에서 빠지지만, 이력과 근거 참조는 유지된다. 실제 삭제는 "가상 데이터 초기화"로만 일어난다. 예외: D-28(연결·이력 없는 노드는 바로 삭제, 그 밖은 숨긴 뒤 「완전히 삭제」로 내용을 지운 자리표시 — `deleted: true`, 그 노드를 가리킨 이력은 남음) (2026-10-23 검토9).
- **중복 판정(R-02 ④):**
  - 같은 유니버스에서 사람은 **같은 사번**이면 중복이다.
  - 사람 이외의 노드는 **같은 유형 + 같은 라벨**이면 중복이다. 라벨은 앞뒤 공백과 대소문자를 무시하고 비교한다.
  - 연결은 **같은 출발 노드·도착 노드·관계 유형이면서 유효 기간이 겹치면** 중복이다.
  - 어느 경우든 저장을 거부하고 기존 노드를 안내한다.
- **필수값(R-02 ③, R-12 ②):**
  - 유니버스: 이름, 단위 라벨, 작성 주체
  - 노드: 유형, 라벨
  - 연결: 양 끝 노드, 관계 유형
  - 사람의 사번은 필수가 아니다. 사번 없음은 R-11의 예외 사례로 다뤄야 하므로 입력 자체는 허용하고 경고만 표시한다.
- **소속 누락(R-14):** 소속 연결이 없는 기간은 "미기재"로 표시하고, 업무 이력은 그대로 이어서 보여 준다.

### 1.6 사람과 조직의 위치

- 업무 유니버스의 "사람" 노드는 그 업무에 관여한 사람을 나타낸다. 소속은 필요할 때만 `소속` 연결로 적는다.
- 조직관리 유니버스는 사람·조직 노드와 소속 변경 이벤트를 **자신의 업무 데이터로** 가진다(00-context "유니버스 개념" 2).
- 업무 유니버스와 조직관리 유니버스의 사람은 **통합할 때 사번으로만** 대응시킨다.
- 프로토타입에서는 조직관리 유니버스가 다른 유니버스의 기준 데이터가 되어 값을 검증하거나 덮어쓰지 않는다. 이 역할은 v0.2 §12-2에 따라 R-09로만 다룬다.

### 1.7 데이터량·보관·인덱스 후보

- **데이터량** [임시 가정 DA-1]:
  - 가상 인물 20~30명, 팀 유니버스 3개(A·B·C)와 조직관리 유니버스 1개
  - 유니버스당 노드 수십~200개, 조직개편 이벤트 2~3회
  - 출처: 정의서 v0.1 §6의 가상 데이터 원칙. 사용자 승인 "진행"(2026-09-30).
  - 업무 내용이나 인물 정보가 더 필요하면 개발자가 사용자에게 요청한다(사용자 요청, 2026-09-30). 요청할 항목은 3단계 R-13 작업에 적는다.
- **보관:** 프로토타입에서는 해당 없음(01-requirements 4절).
- **인덱스 후보:** 파일·브라우저 저장소라 별도 인덱스는 해당 없음. 불러올 때 메모리에 아래 조회 표를 만든다.
  - 사번 → 사람 노드
  - (유형, 정규화 라벨) → 노드
  - 노드 → 이벤트 목록(시간순)
  - 주제 → 노드 목록

## 2. 팀 유니버스 구성 방식 (RQ-4 결정) [2단계 제안]

| 대안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 꼭지 모음 | 팀 유니버스는 자기 노드 없이 업무 유니버스들의 꼭지만 참조한다 | 개념이 깔끔함. 업무 이력이 업무 유니버스에만 존재 | 팀 공통 자료(팀 공지, 팀 규칙)를 둘 곳이 없음. 업무 유니버스를 여러 개 먼저 만들어야 해서 시연 준비가 무거움 |
| B. 직접 생성 | 팀이 유니버스 하나를 만들고, 업무는 그 안의 "업무" 노드로 둔다 | 만들기 쉬움. 시연 데이터 작성이 가벼움 | 업무 하나 = 유니버스 하나(v0.2 §1)와 어긋남. 나중에 업무를 떼어 내기 어려움 |
| **C. 혼합 (선택)** | 모든 유니버스는 **자기 노드를 가질 수 있고, 동시에 다른 유니버스의 꼭지를 참조할 수도 있다** | A와 B가 같은 틀의 두 사용법이 됨. 팀은 직접 생성으로 시작하고, 나중에 업무 유니버스를 분리해 참조로 바꿀 수 있음. 통합(R-11)도 같은 방식(참조)으로 표현됨 | 화면에서 "내 노드"와 "참조된 노드"를 구분해 보여 줘야 함 |

- **결정 D-02: C(혼합).**
  - 사용자가 "지금 고민"이라고 한 질문이 틀 선택이 아니라 **사용 방식 선택**이 되도록 만드는 결정이다. 어느 쪽으로 쓰든 같은 틀 안에서 표현된다.
  - 시연 데이터는 두 방식을 모두 보여 준다(4절 사례): A팀은 업무 유니버스를 참조하는 방식(A 사용법), B팀은 직접 생성 방식(B 사용법)으로 만든다.
- 미검증 전제: 참조와 직접 노드가 섞여도 탐색 화면(R-01)이 이해하기 쉬운가. 검증은 3단계 R-08 대리 검증 때 관찰한다.

### 2.1 CR-4: 층별 보기와 유니버스 묶기 [승인: "1,2,3,4,5 전부 승인 및 진행", 2026-10-03]

- **목적:** 업무 → 팀 → 부서 → 본부로 묶을 때 노드가 폭증하지 않도록, 노드를 복사하지 않고 **층마다 보여 주는 양만** 줄인다.
- **접기:** 상위 유니버스에서 하위 유니버스는 처음에 접혀 있다. 접힌 하위 유니버스는 꼭지와 "위로 드러낼 노드"만 보이고, 나머지 연결은 포함 관계를 따라 올라가 요약 연결(점선)로 보인다. 꼭지를 더블클릭하거나 상세의 「펼치기」·「접기」로 바꾼다.
- **위로 드러낼 노드(기본 규칙):** 꼭지, 담당자(수행 연결이 있는 사람), 최상위 업무(다른 업무에 포함되지 않은 업무), 다른 유니버스와 공유한 주제(확정된 주제 동일성 연결). 노드마다 `exposed`(12.2)로 직접 바꿀 수 있고, 직접 지정이 기본 규칙보다 먼저다.
- **다른 유니버스 노드의 드러내기:** 상위 화면에서 바꾸면 **그 노드의 원래 유니버스 문서에 저장**된다. 화면에 "「원본 유니버스」에 저장됩니다"를 표시한다(D2-4 가).
- **유니버스 묶기:** 사용자가 유니버스 2개 이상과 이름·단위·작성 주체를 정하면 새 유니버스를 만들고 꼭지 참조(`refs`)로 묶는다. 순환·중복·자기 자신·없는 유니버스는 거부한다. 「묶음에서 빼기」는 참조를 지우지 않고 `hidden`·`removed_at`으로 해제 기록을 남긴다.

## 3. 통합 방식 (R-11) [2단계 제안]

| 대안 | 내용 | 판단 |
|---|---|---|
| 복사 병합 | 하위 유니버스의 노드를 새 유니버스에 복사하고 합친다 | 포기. 원본과 사본이 따로 놀아, 하위 유니버스를 수정해도 반영되지 않음 |
| **참조 + 동일성 연결 (선택)** | 새 부서 유니버스는 하위 꼭지를 `Ref`로 참조하고, 합칠 노드 쌍만 `IdentityLink`로 저장한다. 화면은 불러올 때 합쳐진 모습을 계산해 보여 준다 | 원본이 바뀌지 않음(R-11 ⑤). 하위 수정이 자동 반영됨. 사람의 판정 기록이 남음 |

**결정 D-03: 참조 + 동일성 연결.** 통합 절차는 다음과 같다.

1. 사용자가 하위 유니버스(A·B·C)를 선택하고, 새 유니버스 이름과 단위("부서")를 입력한다.
2. **사람 대응:**
   - 사번이 같고 이름도 같으면 `사번 자동`으로 연결한다.
   - 사번은 같은데 이름이 다르면 **충돌**, 사번이 없으면 **사번 없음**이다. 두 경우 모두 확인 목록에 올리고 자동으로 판단하지 않는다(R-11 ③).
3. **업무 후보:**
   - 규칙 기반: 주제 공유 수, 라벨 유사도, 산출물 유형 공유로 후보 점수를 매긴다.
   - LLM 설정이 있으면 후보 이유를 문장으로 덧붙인다(역할 c).
   - 사용자가 후보마다 "같음/다름"을 확정해야만 `IdentityLink`가 생긴다(R-11 ②).
   - 표시(CR-22 마무리, X-40, 사용자 "추천대로" Q1 — 검토 RV12D-17): 후보 이유 문장에서 근거 종류(같은 주제·같은 산출물 유형·이름에 같은 낱말)를 세는 표시용 함수 `candidateEvidenceKinds`로, 근거가 주제 하나뿐인 업무 후보(`isTopicOnlyCandidate`)는 목록 아래 접힌 「주제만 겹친 후보 n건」 묶음에 둔다. 지우지 않고(점수 계산·후보 항목 모양·같음/다름 단추·판정 기록(화면 글은 「지금까지 고른 답」)은 그대로) 통합 확인 제목의 후보 수는 전체 수다. AI가 같은 쌍으로 본 후보는 위에 둔다. 이유 문장 조각(mergePlan의 why)이 바뀌면 어긋나므로 tests/cr22-polish.test.js가 둘이 맞는지 지킨다. 접힌 줄의 후보는 점수 칩(「n점」) 대신 「주제 하나만 겹침」 칩(`TOPIC_ONLY_CHIP`, 점수는 칩의 title로만)을 달고 묶음 설명은 "주제 하나만 겹친 쌍은 점수와 상관없이 같은 업무일 가능성이 낮아 아래로 내렸습니다"이며, 판정으로 패널이 다시 그려져도 펼침 상태는 지도(묶음)별로 유지한다(`ui/merge.js` 모듈 값 `topicOnlyOpen` — 저장하지 않고 통합 확인을 닫으면 지움)(검토 FU7-3·5, 2026-10-26).
   - 표시·되돌리기(처음 사용 8회차 FU8-24·25, 2026-10-26, `ui/merge.js`·`ui/main.js`, 새 판정·저장 형식 없음): ① 「같은 사람(업무)」은 같은 자리에서 「…로 이으면 그래프에서 한 항목으로 보입니다. 이을까요?」(`merge-confirm-q`)·「이어요」(`merge-same-yes`)·「아니요」로 한 번 더 묻고 「다른 …」은 바로 정한다 — 같은 판정은 그래프에서 항목이 합쳐지기 때문. ② 후보 줄마다 두 쪽 근거 한 줄(`merge-sides`: 「이름」 · 지도 「…」 · 사람이면 `personData`의 지금 맡은 업무 최대 `SIDE_WORKS_MAX` 3, 업무면 `cardData`의 담당 글)을 보인다 — 카드 계산을 읽기만 하고 계산 실패 시 지도 이름까지만. ③ 「지금까지 고른 답」의 사람이 정한 줄(`method` human)에는 「다시 묻기」(`merge-reask`): `app.decideIdentity({…, status: 'pending'})`로 `IdentityLink`를 아직 답하지 않은 상태로 되돌리고(새 명령 없음, 이벤트 updated의 before/after가 남아 되감기에 보임) 후보 목록에 다시 올라온다. **사번이 같아 자동으로 이은 줄(`emp_no_auto`)에는 없다** — 다음 묶기에서 다시 이어지므로(limits L-93).
4. 확인하지 않은 항목이 남아 있어도 통합 유니버스는 저장할 수 있다. 미확인 항목은 "확인 대기"로 표시된다.
5. 통합 유니버스는 일반 유니버스와 같은 탐색 화면(R-01)과 인사이트(R-05)를 쓴다(R-11 ④).
6. **주제 동일성(CR-4, 2026-10-03 승인):** 서로 다른 유니버스의 같은 주제(예: 두 팀의 "대사 불일치")도 사람 확인으로만 `IdentityLink`(`kind: topic`)를 만든다. 확정된 주제는 접힌 화면에서도 위로 드러난다(2.1).
7. **확인 대기 목록은 저장하지 않고** 볼 때마다 계산한다. 하위 유니버스가 바뀌어도 목록이 따라가게 하기 위해서다(D3-17). 사람이 판정한 것만 `identity_links`에 저장한다.

## 4. 사례 검증 (가상·마스킹 레코드)

## 5. 실행 형태와 기술 결정

### 5.1 실행 형태 (D-05) [2단계 제안]

제약 조건:
- 심사위원 PC는 알 수 없고, 최소 절차로 실행돼야 한다(A-1).
- 메일로 제출한다. URL 제출도 가능하다고 확인됨(사용자, 2026-10-23) — 공개 위치는 사용자 결정 대기 (2026-10-23 검토9).
- 제출물에 키가 없어야 한다(A-2).
- 개발은 개인 PC에서 Claude Max로 한다.

| 대안 | 심사위원 실행 절차 | 호환성 | 운영·유지보수 | 비용 | 판단 |
|---|---|---|---|---|---|
| 1. Python + Streamlit 로컬 웹 (v0.1 후보) | Python 설치 → 패키지 설치 → 명령 실행 | OS와 무관하지만 설치 부담이 큼 | 코드 작성이 쉬움 | 무료 | 포기: A-1(최소 절차) 위반 가능성이 큼 |
| 2. Windows 실행 파일(Python 패키징) | 더블클릭 | Windows만 가능. 백신 경고 가능성. 파일이 커서 메일 첨부 제한 위험 | 빌드가 번거로움 | 무료 | 포기: OS 제한, 메일 용량 위험 |
| **3. 정적 웹 앱(HTML·JS 한 폴더, 브라우저로 열기) (선택)** | 압축 해제 → `index.html` 더블클릭 | 최신 브라우저(Chrome, Edge 등)만 있으면 OS 무관 **[가정: 실측은 Windows의 Chrome·Edge 154뿐. macOS·Firefox·Safari는 미확인(2026-10-02 검토)]**. 인터넷 없이도 동작(라이브러리를 함께 넣음) | 서버 없음. 초기화·내보내기가 쉬움 | 무료. LLM 사용 시 API 크레딧만 | 선택 |

**결정 D-05: 3. 정적 웹 앱.** 사용자 승인 "진행", 2026-09-30.

- **선택 이유:** 심사위원 PC 환경을 알 수 없고(A-1), 메일로 제출하므로, 설치 없이 OS와 관계없이 더블클릭 한 번으로 실행되는 방식이 이 프로젝트 조건에 가장 맞는다. 그래프 탐색 화면(R-01)도 브라우저가 가장 잘 그린다.
- **CORS와의 관계:** CORS는 선택 이유가 아니라, 이 방식을 택했을 때 지켜야 하는 **제약**이다(P-1).
- **포기한 이점:** Python에 비해 데이터 처리 라이브러리가 적다. 프로토타입 규모(DA-1)에서는 문제되지 않는다고 판단한다.

이 결정에는 미검증 전제가 두 가지 있다. 3단계의 첫 작업에서 실측한다.

| 전제 | 확인한 내용 | 영향 | 검증 방법 |
|---|---|---|---|
| **P-1** 더블클릭 실행 | `file://`로 연 HTML이 JS 모듈을 불러오면 CORS 오류가 난다(MDN "JavaScript modules", 확인일 2026-09-30) | 빌드 결과를 **모듈을 쓰지 않는 번들 1개(또는 HTML 1개에 인라인)**로 만들어야 함 | 빈 화면 + 그래프 라이브러리만 넣은 최소 파일을 Chrome·Edge에서 더블클릭으로 연다 |

**P-1 실측 결과 (T-01, 2026-09-30): 통과.** Chrome 154.0.8037.58과 Edge 154.0.4258.37에서 `dist/index.html`(일반 `<script src="app.js">`, 모듈 없는 IIFE 번들. 2026-10-01부터는 같은 스크립트를 HTML 안에 넣은 파일 하나)을 `file://`로 열었을 때 그래프 표시, 클릭 상세, 노드 추가가 동작했다. 인터넷 요청을 모두 막은 상태에서도 동작했고 외부 요청은 0건이었다. 자동 점검(`tools/browser-check.mjs`) 뒤 사용자가 탐색기에서 직접 더블클릭해 확인했다. 대안 K-3(인라인 단일 HTML → 로컬 서버)은 쓰지 않는다. 상세: `docs/tech-record.md` 5절.

**P-1 해결 방안** (사용자 질문 "우회나 출처 지정으로 해결 가능한지" 반영, 2026-09-30):

- **오류를 일으키는 방식을 쓰지 않는다.**
  - 모듈 스크립트(`type="module"`)와 `fetch()`로 로컬 파일을 읽는 방식을 쓰지 않는다.
  - 대신 일반 스크립트 파일(또는 HTML 안에 넣은 스크립트)과 JS로 감싼 샘플 데이터를 쓴다.
  - 사용자가 고른 JSON 파일은 파일 선택 창으로 읽는다. 이 방식은 CORS 대상이 아니다.
  - 일반 스크립트가 `file://`에서 동작하는지는 **P-1 실측으로 확인**한다.
- **"출처 지정"은 해당 없다.** CORS 허용 출처는 **서버가** 응답 헤더로 지정한다. 더블클릭 실행에는 서버가 없으므로 지정할 곳이 없다.
- **브라우저 보안 옵션 끄기는 쓰지 않는다.** 실행 옵션으로 로컬 파일 접근을 허용하는 우회는 심사위원 PC에 적용할 수 없고, 보안상 권하지 않는다.
- **최후 대안:** 제출물에 작은 로컬 서버 실행 파일을 넣는다. 실행 절차가 늘어나므로(A-1), 위 방식이 실패할 때만 쓴다.
- **P-2(Claude API)의 CORS는 별개다.** Anthropic 서버가 허용 여부를 정하고, 브라우저 직접 호출용 헤더가 있다(비공식 자료). 이 호출은 개발 PC·영상에서만 필요하며, 실패하면 D-07b(로컬 중계)로 대신한다. 심사위원 PC는 LLM을 호출하지 않으므로 이 문제와 무관하다.
| **P-2** 브라우저에서 Claude API 직접 호출 | `anthropic-dangerous-direct-browser-access: true` 헤더로 가능하다고 비공식 자료(Simon Willison, 2024-08-23)에 나온다. Anthropic 공식 문서에서는 **미확인** | 실패하면 개발 PC·영상용으로만 작은 로컬 중계 프로그램이 필요(대안 D-07b) | 개발 PC에서 테스트 키로 호출 1회. `file://` 출처에서도 되는지 함께 확인 |

### 5.2 저장 (D-06) [2단계 제안]

| 대안 | 판단 |
|---|---|
| **브라우저 저장소 + JSON 가져오기·내보내기 + 초기 가상 데이터 내장 (선택)** | 설치가 필요 없고 초기화가 쉬움(01-requirements 4절 "초기 상태 복귀") |
| 로컬 파일 직접 쓰기 | 브라우저 보안상 파일을 자동으로 쓸 수 없고 매번 사용자 확인이 필요 → 포기 |
| 로컬 DB·서버 | D-05와 충돌 → 포기 |

- 저장 단위는 유니버스 1개 = JSON 문서 1개다. 구성은 `universe`, `nodes`, `edges`, `events`, `refs`, `identity_links`다.
- 미검증 전제 **P-3:** `file://`에서 브라우저 저장소(localStorage 또는 IndexedDB)가 유지되는가. 브라우저마다 다를 수 있다. 검증은 P-1과 같은 최소 파일로 저장 → 새로고침 → 확인한다. 유지되지 않으면 "세션 동안만 유지 + 내보내기 안내"로 축소한다.
- **P-3 실측 결과 (T-01, 2026-09-30): 통과.** Chrome·Edge(위 P-1과 같은 버전)에서 `localStorage`에 저장한 노드가 새로고침 뒤에도, 브라우저를 정상 종료했다 다시 연 뒤에도 유지됐다. 저장소 접근이 막히면 `W-STORAGE` 배너가 뜨고 샘플을 읽기 전용으로 연다. 대안 K-4(세션 유지 + 내보내기)로 축소하지 않는다.
  - 관찰: 저장 직후 몇 초 안에 브라우저를 강제 종료하면 마지막 변경이 디스크에 기록되지 않을 수 있다. 시연 안내에 내보내기를 권한다.

### 5.4 LLM 연결부 계약 (D-07) [2단계 제안]

- **입력:** 작업 종류(`초안`/`인사이트 설명`/`업무 후보 이유`/`업무정의서 변환`(CR-3)), 근거 목록(노드·이벤트 ID와 그 내용). 업무정의서 변환의 입력은 문서 원문이고 출력은 12.2 유니버스 문서다(12.9).
  - 근거 목록에는 가상 데이터만 들어간다.
  - 근거로 고른 것만 보내고, 전체 유니버스는 보내지 않는다.
  - **(CR-20 보충 — CR-15·CR-19 뒤 실제로 보내는 범위, 코드 확인 2026-10-25):** 초안·인사이트 설명(B)은 그 항목의 근거 글만(`llm/evidence-text.js`). 문서 AI 변환(A)은 붙여 넣은 원문. AI 연관 찾기(C)는 묶은 지도의 하위 지도 업무 **전부**를 보낸다 — 업무마다 이름·설명·속성과 그 업무가 만드는 산출물·잇는 주제의 이름(업무 300개·합계 10만 자·업무당 1500자 상한, `llm/ai-candidates.js` `collectWorks`·`AI_CANDIDATES_MAX_*`). 글로 추가(R-29)는 붙여 넣은 글과 지금 지도의 항목 이름·유형(최대 200개, `llm/ai-extract.js` `existingItems`). 어느 경우에도 유니버스 문서(JSON)·이력 전체를 그대로 보내지는 않는다. 앱 도움말 「키와 데이터」의 외부 전송 설명과 같다(RV10S-13).

  - **(CR-17 H, 2026-10-24) 키 없이 「Claude API」를 고른 경우:** 규칙 기반이 아니라 **사전 생성 → 규칙 기반** 순으로 대체한다(`providers.js`의 키 없는 공급자가 사전 생성 공급자를 바탕으로 하고, 문서 변환·AI 연관 찾기는 키가 필요해 안내만). 사전 생성 문장도 지금처럼 근거·지문 검사를 거친다. 안내는 쓴 방식을 그대로 말한다: 사전 생성 문장을 썼으면 "키가 없어 미리 받아 둔 문장(사전 생성)으로 보여 줍니다 — 「설정」에서 키를 넣으면 Claude가 실시간으로 다시 씁니다", 하나도 못 썼으면(내가 만든 지도 등) "키가 없어 기록을 그대로 모은 문장(규칙 기반)으로 보여 줍니다 …". 고장이 아니라 안내이므로 "연결 오류" 머리말을 붙이지 않는다. 키가 있는데 호출이 실패하면 호출 전 문장(사전 생성 포함)을 유지하고 원인을 표시한다(C15-14).

  - (CR-15, 2026-10-23) 키는 설정 화면에서 입력하고 **그 브라우저 저장소에만** 둔다(`wu:v1:settings.apiKey`). 파일·저장소 코드·내보내기·내용 포함 HTML·폴더 거울·이력에는 절대 넣지 않는다. 제출물에는 키가 없어 기본은 사전 생성·규칙 기반이고, 키를 넣은 브라우저에서만 실시간 호출한다. 호출은 공식 `@anthropic-ai/sdk`(브라우저 허용 옵션 `dangerouslyAllowBrowser: true`, 공식 문서 "내부 도구·단기 키에 한해")를 빌드에 함께 묶어 쓴다. 모델 기본 `claude-opus-5-5`(상수 한 곳, 설정에서 바꿀 수 있음). 응답은 구조화 출력(`output_config.format`)으로 받아 스키마 검증 → 근거 ID·지문 검증 → **원문 인용(quote) 부분 문자열 검증**을 거친다. 연결부는 비동기(규칙 기반 결과를 먼저 그리고 항목 단위 교체, 시간 초과 상수, 응답은 (조회 키, 지문)으로 캐시).
  - 제출 전 점검: 제출 폴더에서 키 형식 문자열을 검색해 0건이어야 한다(R-15 ③).
- **모델 선택:** 2단계에서 정하지 않는다. 3단계에서 Claude API 모델 목록과 요금을 확인한 날짜와 함께 기록한다. → CR-15: 기본 `claude-opus-5-5`(상수 한 곳, 설정에서 바꿀 수 있음 — 위 키 보관 항목, CR-20 정리).
- **대안 D-07b:** P-2가 실패하면 개발 PC에서만 실행하는 작은 로컬 중계 프로그램을 둔다. 이 프로그램은 제출물에 넣지 않는다.

### 5.5 인사이트 계산 규칙 (D-08) [2단계 제안]

모든 인사이트는 LLM 없이 계산하고, LLM은 설명 문장만 쓴다.

| 인사이트 | 규칙 | 데이터 부족 조건 |
|---|---|---|
| **유사 경험자(P0)** | 선택한 업무와 주제·산출물 유형·라벨 토큰을 공유하는 다른 업무를 찾아 점수화한다. 그 업무를 `수행`한 사람을 점수순으로 보여 주고, 근거로 공유 주제와 업무 노드를 붙인다. 현재 담당자는 제외한다. **(CR-17 B, 2026-10-24)** ① 맨 위에 「직접 해 본 사람」: 기준 업무를 예전에 `수행`했고 연결 기간이 기준일에 끝난 사람(기준 업무의 이전 담당, 기간 표시, 최근에 끝난 순, 현재 담당·제외 대상은 뺌)을 따로 묶는다. 비슷한 일도 했으면 같은 카드에 이어 보인다 ② 역할 이름만 있는 노드(사람 하위 유형 「역할」)는 아래 「사람 미확인(역할 이름)」 묶음으로 나눈다 ③ 주제·산출물을 공유하지 않아도 업무 이름 낱말이 같은 업무(예: 「2025 행사」↔「2026 행사」)의 수행자는 낮은 점수(이름 낱말 가중치만)로 후보에 넣고 이유를 "이름에 같은 낱말 「…」 — 같은 일인지 확인"(상수 `NAME_ONLY_NOTE`)으로, 칩 「이름만 같음」과 함께 표시한다(오탐 가능 — limits L-54). 낱말은 기존 규칙(공백·구두점으로 나눈 2자 이상, 흔한 낱말 제외)을 그대로 쓴다. 코드: rules/insight.js `similarExperts`(`direct`·`people`·`roles`), 코드 확인 2026-10-24(커밋 84e53cc) | 주제·산출물 연결이 없고 이름 낱말이 같은 다른 업무도, 이전 담당도 없는 업무 |
| 밀집/공백 | 조직(또는 하위 유니버스)별 활성 업무 수와 수행 인원 수를 집계한다. 담당자가 없는 업무(공백)와 1인이 N개 이상을 맡은 경우(밀집)를 표시한다. N은 화면에서 조정하며 기본값은 정하지 않고 3단계 데이터로 정한다 | 수행 연결이 없는 유니버스 |
| 반복 비효율 | ① 같은 업무에서 인수인계 이벤트가 2회 이상인데 이후 인수인계가 이전 인수인계서를 `참조`하지 않음. ② 같은 주제의 메모·인수인계가 서로 다른 업무 2곳 이상에서 반복됨. 포함(상위–하위)으로 이어진 업무는 한 업무로 세고, 주의사항·해결됨 범주의 메모는 세지 않는다(결정 D3-32). 근거 이벤트를 목록으로 보여 준다 | 인수인계·메모 이벤트가 2건 미만 |
| 흐름 변화 | 기간(월·분기)별 이벤트 수와 업무·사람 변화를 시간 슬라이더로 보여 준다 | 이벤트 시점 범위가 한 기간 이하이거나, 마지막 입력 이후 기간 |

### 5.6 규칙 기반 인수인계 초안 (D-09) [2단계 제안, CR-6으로 10개 항목으로 보강: 사용자 승인 "둘 다 진행해", 2026-10-01. CR-17 E로 11개 항목(「받는 범위와 담당 공백」 추가): 사용자 승인 "전부 권장대로 진행", 2026-10-24]

아래 항목은 고정이며, 항목마다 근거를 찾는 규칙이 정해져 있다. 근거가 없으면 "이력 부족"으로 표시하고 내용을 만들지 않는다.

- **보강 이유:** 처음 8개 항목(개요·세부 업무·선후행·산출물·관계자·최근 이슈·이전 인수인계·유사 경험자)은 업무의 구조와 이력만 다뤄, 받는 사람이 실제로 쓸 "절차·주의사항·마감·진행 중인 일·연락처"가 빠져 이력을 나열한 것처럼 보였다(사용자 확인, 2026-10-01). 03-plan 7.2가 조력자에게 받을 인수인계 항목으로 든 "진행 중 건, 주요 연락처, 주의사항, 관련 문서 위치"를 반영한다.
- **데이터 틀은 바꾸지 않는다(R-07).** 업무 고유 정보는 12.2의 자유 속성(`attrs`)과 메모로 담는다. 아래 속성 이름은 **약속**이며, 없으면 그 항목은 "이력 부족"이 된다.

| 항목 | 근거를 찾는 규칙 | 쓰는 데이터 |
|---|---|---|
| 업무 개요 | 꼭지 또는 업무 노드의 설명 | `description` |

- 선후행 항목은 "세부 업무·절차"에 합쳤다.

- 메모는 범위 업무가 속한 유니버스의 것만 쓴다(주제를 함께 쓰는 다른 업무의 메모가 섞이지 않게).
- LLM 설정이 있으면 같은 근거로 문장만 다듬는다(5.4). 데이터에 없는 내용은 LLM도 만들 수 없다.
- **CR-17에서 정하지 않은 것(1차 후):** 「최근 바뀐 것」(최근 90일 속성 수정 이력) 항목은 넣지 않는다(E 승인 범위 밖). 항목 수는 11개다.

### 5.6.1 초안 확정 (CR-8) [승인: "추천하는 걸로 구현", 2026-10-03]

- **동작:** 초안 아래 「확정해 인수인계서로 저장」 → 확인 창 → 초안 대상의 유니버스에 저장한다(팀·부서 화면에서 하위 유니버스 업무를 확정하면 그 원본 유니버스).
  - 인수인계서: 산출물 노드(하위 유형 `인수인계서`, 없으면 자동 등록). 이름 "날짜 대상 인수인계서"(같으면 (2)…). 설명 = 확정본 글. 2000자를 넘는 부분은 `본문(이어서 N)` 속성. 속성: 확정자("사용자(이 브라우저)" — 로그인이 없음. 설정의 작성자 이름이 있으면 그 이름, CR-12 D·D-24. 통합 판정의 `decided_by`에도 같은 이름이 쓰인다), 확정 시각, 보내는 사람, 받는 사람, 초안 생성 방식.
  - 연결: 업무 → 인수인계서 `produces`(메모 "인수인계 초안 확정"). 같은 유니버스의 업무가 없으면 꼭지 → `contains`.
  - 이력: 업무마다 `handover` 이벤트(`artifact_id` = 인수인계서, `previous_handover_id` = 그 업무의 바로 앞 인수인계, 날짜 = 오늘).
- **인수인계할 업무:** 대상이 업무면 그 업무, 꼭지면 범위 업무 중 보내는 사람이 맡았던(수행 연결) 업무. 없으면 확정하지 않고 이유를 알린다(D3-28).
- **막는 경우:** 같은 날·같은 업무·같은 보내는/받는 사람의 인수인계가 이미 있으면 거부. 읽기 전용이면 거부.
- **효과:** 다음 초안의 「이전 인수인계」에 인수인계서가 근거로 나오고, 반복 비효율 ①은 바로 앞 인수인계를 이어받은 것으로 본다.
- **하지 않는 것:** 담당 시작·종료(`assign_start/end`)와 수행 연결 기간은 바꾸지 않는다(인계 문서 확정과 담당 변경은 따로 기록). **→ CR-18-6(2026-10-24, D-36 ③)으로 선택 칸을 더했다:** 확정 버튼 위 「담당도 넘기기」(기본 꺼짐)를 켜면, 보내는 사람의 진행 중(끝 날짜 없는) 수행 연결 중 확정을 저장하는 유니버스 안의 업무를 오늘로 끝내고(`assign_end`) 받는 사람의 수행을 오늘부터 시작한다(`assign_start`). 확정과 같은 명령 사슬·같은 기록 시각이라 한 번의 기록이고, 어느 하나라도 실패하면 인수인계서·이력까지 아무것도 저장하지 않는다. 받는 사람이 이미 수행 중인 업무는 건너뛰고, 두 사람이 그 유니버스 밖에 있으면 칸이 꺼진 채 이유를 보인다(`transfer_scope`). 계산은 `view/transfer.js`. 끄면 예전 그대로다. **→ CR-20 ④(2026-10-25, D-38 ④):** 확정과 따로, 업무 상세에 「담당 바꾸기」(날짜 고르기, 선택 「인수인계 기록도 남기기」 — 인수인계서 없이 `handover` 이력만)를 더했다(5.3). 확정 때 「담당도 넘기기」는 그대로 오늘만이다.
- **G 결정 (CR-12, 2026-10-13): 대사 확인 → 인수인계서 「산출」 연결은 바꾸지 않는다.** 조력자가 확정 연결(업무 → 인수인계서 `produces`)이 "산출"로 보이는 것이 어색하다고 지적했다. 연결 메모("인수인계 초안 확정")와 상세 문구로 "이 업무의 인수인계 기록"임을 드러낸다. 이유: 산출 → 참조로 바꾸면 확정 흐름·사전 생성·초안 근거·테스트가 함께 바뀌어 회귀 위험이 크다.

### 5.6.2 표준 양식 (CR-10 A, R-16) [승인: "우선 전부 권장대로", 2026-10-04]

- **목적:** 사람마다 업무를 다르게 넣으면 묶었을 때 비교·인사이트가 맞지 않는다(카드승인 38개와 월말 정산 10개처럼). 그래서 "어디까지 노드로 쪼개고, 업무 노드에 무엇을 채우는지"를 한 가지로 약속하고, 앱이 빠진 것을 알린다.
- **데이터 틀은 바꾸지 않는다(R-07).** 5.6의 속성 약속(`attrs` 이름)을 넓힌 것이다. 스키마에 필수 필드를 더하지 않고, 저장·가져오기를 막지 않는다(D-16).
- **쪼개는 단위:** **대표 업무의 「절차」 속성으로 적는다(처리 단계를 노드로 만들지 않는다).** 조력자 의견(2026-10-12): "보기 편한 건 월말 정산(10개)이 더 편하다", 사용자 "전부 추천으로 진행"(2026-10-13). 참고 기준은 CR-5의 "월말 정산 수준"(업무당 노드 10~20개, 업무 노드 하나에 설명·속성 약 100~180자, review-2026-10-03 6절 비교표).
- **업무 노드의 권장 속성:**

| 속성 이름(attrs) | 권장 여부 | 비었을 때 | 근거 |
|---|---|---|---|
| `description`(설명) | 권장 | "권장 항목 비어 있음"에 셈 | 5.6 업무 개요 |
| `절차` | 권장(조력자: 꼭 필요) | 〃 | 5.6 세부 업무·절차 |
| `주기` | 권장(조력자: 꼭 필요) | 〃 | 5.6 일정·마감 |
| `마감` | 권장(조력자: 꼭 필요) | 〃 | 5.6 일정·마감 |
| `주의사항` | 권장(조력자: 꼭 필요) | 〃 | 5.6 주의사항·노하우 |
| `사용 시스템` | 선택(권장 항목에 세지 않음) | 〃 | 5.6 세부 업무·절차 |
| `관련 문서` | 권장(조력자 의견으로 더함). 속성이 비어 있어도 업무에 산출·참조로 이어진 산출물이 있으면 채운 것으로 본다 | 〃 | 조력자 의견 2026-10-12 |

- **다른 유형의 권장 항목:** 1차 제출에서는 업무만 점검한다(사람 `연락처`, 산출물 `위치`는 권장에 넣지 않고 약속만 둠). 주제는 권장 항목 없음.
- **구현(T-20 최소판, 2026-10-13):** `rules/form.js`(STANDARD_FORM 상수 한 곳, `workFormMissing`·`formReport`), 상세 패널 한 줄(`form-missing`), 가져오기 미리 보기 요약(`import-form`). 저장·가져오기를 막지 않는다. 같은 뜻의 다른 속성 이름은 맞춰 주지 않는다(답이 없으면 값, 결정 T20-1).
- **알림:** `W-FORM-MISSING`(권장 항목 n개 비어 있음, 빈 항목 이름 목록). 상세 패널에서는 그 노드 기준, 가져오기 미리 보기에서는 전체 건수와 노드 목록. 막지 않는다.
- **속성 이름이 약속과 조금 다를 때**(예: "마감일"): 답이 없으면 다른 이름으로 보고 알림을 띄운다(되돌리기 쉬운 쪽). 같은 뜻의 이름을 맞춰 줄지는 〔사용자 결정〕.
- **값의 위치:** 권장 속성 목록은 코드 한 곳의 상수에 둔다(위치는 구현 때 정해 이 줄에 적는다).
- **예외 목록:** R-13 ②의 "이력 부족" 시연용으로 일부러 비운 가상교육팀 「신규 교육 과정」, 그리고 카드승인 샘플(U-K1) — 양식을 따르지 않는 비교 자료로 남김(T20-2, 사용자 "전부 추천으로 진행" 2026-10-13. 목록은 `tests/form.test.js` EXCEPT_UNIVERSES). 노드가 많은 유니버스에는 「나눠 보세요」 안내를 띄운다(아래 앱 안 안내, S-5).
- **앱 안 안내:** 실행 안내와 `docs/가져오기-사용가이드.md`에 "이렇게 넣는다" 1쪽(쪼개는 단위, 권장 속성, 좋은 예·나쁜 예 각 1개). 앱 화면에서는 (1) 새 유니버스의 「첫 업무(선택)」 칸이 업무·담당자·주기·마감·산출물을 표준 양식대로 넣고 개요에 「처음 할 일」 3단계를 보인다(S-1~S-4) (2) 유니버스 자신의 노드(꼭지 제외)가 `STANDARD_FORM.splitAbove`(25)를 넘으면 개요에 「나눠 보세요」 안내를 보인다(S-5). 둘 다 막지 않는다(D8-9).

| 문자열 | 라벨은 1~100자다. 중복 비교는 앞뒤 공백을 제거하고 영문 소문자로 바꾼 값으로 한다. 한글은 NFC로 맞추고, 연속 공백·특수 공백은 한 칸으로 본다. 사번은 대문자로 맞춰 비교한다(검토 2-9) |
| 숨김 | `hidden: true`. 삭제 필드는 두지 않는다(D-04). 예외: 「완전히 삭제」한 노드는 `deleted: true`(hidden 유지)인 자리표시로 남는다(D-28, 12.2) (2026-10-23 검토9) |

| `hidden` | boolean | 필수(기본 false) | |

관계 유형과 허용 조합은 다음과 같다. 목록 밖의 조합은 저장을 거부한다(`E-PAIR`).

| `core_type` | 의미 | 허용 조합(출발 → 도착) |
|---|---|---|
| `contains` | 포함 | root → 꼭지 이외 모든 노드, work → work |
| `performs` | 수행 | person → work |
| `produces` | 산출 | work → artifact |
| `precedes` | 선후행 | work → work |
| `belongs_to` | 소속 | person → org, org → org |
| `relates_to` | 관련 | 꼭지 이외 모든 노드 → topic |
| `references` | 참조 | 꼭지 이외 노드 → 꼭지 이외 노드 |

**events[]**

공통 필드:

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | 필수(자동) | `E-…` |
| `type` | enum | 필수 | 아래 유형 표 참고 |
| `occurred_at` | date | 필수 | 업무 시점 |
| `recorded_at` | datetime | 필수(자동) | 입력 시각 |
| `source` | enum | 필수(자동) | `user`/`sample`/`system` |
| `payload` | object | 유형별 | 아래 표 참고 |
| `note` | string | 선택 | |

유형별 `payload`:

| `type` | 뜻 | `payload` |
|---|---|---|
| `created`, `hidden` | 생성, 숨김 | `{target_kind, target_id}`. `target_kind`는 `node`·`edge`·`ref`(꼭지 참조 추가·해제, `target_id` = 하위 유니버스 ID, CR-4)·`identity_link`(통합 판정, CR-7) |
| `updated` | 수정 | `{target_kind, target_id, before: {…바뀐 필드}, after: {…}}`. `target_kind`는 `node`·`edge`·`identity_link` |
| `assign_start`, `assign_end` | 담당 시작·종료 | `{person_id, work_id}` |
| `handover` | 인수인계 | `{work_id, from_person_id, to_person_id, artifact_id?, previous_handover_id?}` |
| `affiliation_change` | 소속 변경 | `{person_id, from_org_id?, to_org_id?}`. 없는 값은 "미기재"(R-14) |
| `memo` | 메모 | `{target_id?, topic_ids?: [], category?, resolves_id?}`. `category`는 `issue`(기본)·`caution`·`in_progress`·`resolved`(CR-6). `resolves_id`(선택, C12-8 승인 2026-10-13): 범주 `resolved`에만, 같은 문서의 메모 이벤트 ID. 있으면 그 메모 하나만 닫고, 없으면 같은 대상(없으면 같은 주제 집합)의 앞선 메모를 닫는다 |

- `previous_handover_id`는 반복 비효율 규칙 ①에서 "이전 인수인계서를 참조했는가"를 판정할 때 쓴다(D-08).

**refs[]**

`{child_universe_id, added_at, hidden?, removed_at?}`. 부모 문서에 저장한다. 순환이면 거부한다(`E-CYCLE`). 「묶음에서 빼기」는 지우지 않고 `hidden: true`와 `removed_at`을 남긴다(CR-4).

**identity_links[]** (통합 유니버스만)

| 필드 | 형식 | 설명 |
|---|---|---|
| `id` | string | `I-…` |
| `a`, `b` | 전역 참조 | 같다고 판정할 두 노드 |
| `kind` | enum | `person`/`work`/`topic`(CR-4, 사람 확인만) |
| `method` | enum | `emp_no_auto`(사번 자동. 사람만 가능) / `human`(사람 확인) |
| `status` | enum | `pending`(확인 대기) / `confirmed` / `rejected`. 거부한 쌍은 다시 제안하지 않는다 |
| `score` | number | 선택. 후보 점수 |
| `reason` | string | 선택. 규칙 기반 또는 사전 생성 이유 |
| `decided_by`, `decided_at` | string, datetime | `human`일 때 필수 |

### 12.3 사전 생성 결과 파일 (CR-1)

```json
{
  "schema_version": "1.0",
  "generator": "Claude Code (개발 시 작성)",
  "generated_at": "2026-10-…T…+09:00",
  "items": [
    {
      "task": "handover",
      "target": "U-A1/N-001",
      "evidence_ids": ["U-A1/N-003", "U-A1/E-004"],
      "sentences": [
        { "text": "…", "evidence_ids": ["U-A1/N-003"] }
      ]
    }
  ]
}
```

- `task`: `handover`(초안) / `insight_explain`(인사이트 설명) / `work_candidate_reason`(업무 후보 이유) / `doc_to_universe`(업무정의서 변환, CR-3. 결과는 `sentences` 대신 12.2 문서이며 12.9 규칙을 따른다)
- 조회 키: (`task`, `target`, 항목 `item`, 보내는 사람>받는 사람, 정렬한 `evidence_ids`). 항목·사람은 초안에만 쓴다. 항목 단위라 데이터가 바뀐 항목만 규칙 기반으로 돌아가고, 사람이 다르면 다른 사람 이름이 든 문장을 쓰지 않는다(CR-7, D3-10). 키가 맞지 않으면 낡은 결과로 보고 규칙 기반을 쓴다(K-9).
- 문장의 `evidence_ids`가 실제 데이터에 없으면 그 문장은 버린다(D-07).

- 규칙: `model`, `view`, `merge`, `rules`, `llm`은 브라우저 기능(DOM, 저장소)을 쓰지 않는다. 그래야 Node에서 테스트할 수 있다.
- 해석(CR-7, D2-8): `ui`는 계산만 하는 순수 함수(`rules`·`view`·`llm`)를 직접 부를 수 있다. 저장·상태 변경은 반드시 `app`을 거친다.

**핵심 흐름 3가지**

1. **자료 저장(R-02, 〔C〕 R-18):**
   1. ui 입력 → `app.addNode`(하나) 또는 `app.applyBatch`(여러 개, 표 입력 창. 이름은 구현 때 확정)
   2. `model` 검증. 실패하면 오류 코드를 ui에 돌려준다. 일괄이면 명령을 차례로 적용하고, 하나라도 실패하면 **원래 문서를 바꾸지 않고** 행별 오류를 돌려준다(전부 아니면 전무, D-18).
   3. 성공하면 새 문서와 이벤트(`created`, 수정이면 `updated`의 변경 전후 값)가 생긴다.
   4. `store`에 **한 번** 저장한다. 저장이 실패하면 화면의 문서를 바꾸지 않고 `W-STORAGE`를 알린다.
   5. `view`를 다시 계산하고 그래프를 갱신한다.
   - 노드 하나를 넣으면서 꼭지에 잇는 경우(「노드 추가」의 꼭지 연결)도 노드 추가 + 연결 추가를 한 묶음으로 저장한다. applyBatch(addNode + addEdge op)로 한 번에 저장한다(2026-10-18 구현, tech-record 48절) (2026-10-23 검토9).
2. **인수인계 초안(R-03·R-04·R-15):**
   1. ui에서 업무·보내는 사람·받는 사람을 고른다.
   2. `rules`가 11개 항목(CR-6·CR-17 E, 5.6)과 근거 ID를 만든다. 근거가 없는 항목은 "이력 부족"이다.
   3. `llm`이 공급자에 따라 사전 생성 결과를 조회하거나 API를 호출하고, 근거 ID를 검증한다. 실패하면 규칙 기반 문장을 쓴다.
   4. ui가 항목별 문장, 근거 링크, 생성 방식을 표시한다.
3. **통합(R-11):**
   1. ui에서 하위 유니버스들을 선택한다.
   2. `merge`가 사번 자동 연결(`confirmed`)과 확인 목록(`pending`)을 만든다.
   3. 새 부서 유니버스 문서를 만든다(`refs`와 `identity_links`만 가짐).
   4. `store`에 저장한다.
   5. 사용자가 확인하면 `status`를 바꾸고 이벤트를 기록한다.
   6. `view`를 다시 계산한다.

### 12.9.1 CR-5: 앱 안 규칙 기반 초벌 변환 [확정: "CR-5는 ②로 확정, 변환 세분화는 월말 정산 수준으로", 2026-10-03]

- **흐름:** 사용자가 「가져오기·내보내기」 창에 문서를 붙여 넣는다(또는 .md·.txt 파일, 「예시 문서 넣기」) → `llm/connector.convertDocumentWith` → 공급자가 문서 변환을 할 수 있으면 그 결과, 아니면 `rules/doc-convert.convertDocument`(규칙 기반) → `model/import.previewImport`(12.2 검증·원문 근거·표시 보존·같은 ID) → 미리 보기에서 이름·작성 주체 확인 → 사람이 「가져오기」 → `app.importUniverse` 저장.
- **공급자:** 규칙 기반만·사전 생성 → 규칙 기반(사전 생성은 내장 샘플용이라 새 문서 결과가 없다고 안내). Claude API·사내 LLM·실패 흉내 → 규칙 기반 + 원인(R-04 ③). 공급자 결과를 쓰려면 12.2 검증(작성 주체 빈칸만 예외)과 모든 노드의 원문 근거를 통과해야 한다.
- **읽는 구조:** 마크다운 제목(#, 번호 "4.1" → 원문 §4.1), 표(머리글 있으면 "머리글: 값"), 번호 목록, 글머리표, 인용. 제목 없는 글은 업무 하나로 만들고 알린다.
- **일반 글(한글·워드에서 복사, N-1, 사용자 "1,2,3,4,5 전부 승인 및 진행"(2026-10-03)):** 마크다운 표시(#, |)가 없으면 첫 줄을 문서 제목으로, "1. 개요"·"4.1 …"·"가. …"·"■ …"·"【…】"처럼 짧고 문장(…다, 마침표)이 아닌 줄을 절 제목으로 본다. "N."은 목록과 모양이 같아 바로 앞 제목 번호의 다음 차례일 때만, "가."는 그 절 안의 차례가 맞을 때만 제목이다. □ ○ ● ▪ ※ 등은 글머리표, 1) (1) ① 가. 는 번호 목록, 탭으로 나뉜 줄은 표(첫 칸이 구분·항목·역할 등이면 머리글). "가." 소제목의 원문 번호는 §5-가.
- **절 분류(제목 낱말, 괄호 안은 보지 않음, 앞의 것이 먼저):** 산출물 → 미확정·질문·리스크 → 흐름·절차 → 이해관계자·역할 → 범위 제외 → 범위 → 개요 → 그 밖은 주제.
  - **제목 낱말 보강(W8·CR-17 J, 2026-10-24):** 제목 **전체**가 "담당"·"주 담당"·"담당 및 검토"·"담당자/검토자"류이면 이해관계자·역할 절, "관련 문서"·"참고 자료"·"첨부 서류"·"관련·참고 문서"류이면 산출물·문서 절로 본다("담당 업무"·"담당 범위"·"관련 법령"·"문서 관리 규정"은 아님). 이 두 제목으로 **새로 잡힌 절에만** 아래 CR-17 J의 읽기를 적용하고, 원래 이해관계자·산출물 절(제목 "담당자"·"역할"·"이해관계자"·"산출물" 등)은 위 v1 표 그대로 읽는다(고정 사례 W8d).
- **규칙 v1(세분화: 월말 정산 수준, 노드 10~20개):**

- **지어내지 않기:** 모든 노드에 `attrs.원문`. 기간 없는 추정 담당은 "지금 담당"으로 계산되므로 미리 보기에 건수를 알린다. 같은 유형·이름은 하나로 합치고 근거를 잇는다. 설명·절차·주의사항 등 항목 글이 2000자를 넘으면 자르고 알린다. 입력 전체가 200,000자를 넘으면 변환하지 않고 거부한다. 첫 칸이 빈 표 행(병합 셀)은 앞 행에 붙이고, 이름에서 뺀 [가정]·[미확인] 글은 `attrs.표시`에 남긴다. 제목이 같은 절은 주제 하나로 합친다. 작성 주체가 원문에 없으면 비워 두고 미리 보기에서 입력받는다(R-12 필수).

- **함께 넣은 것(D-06):** 같은 창의 「JSON 파일」 탭(내보낸 유니버스·개발 중 변환해 둔 파일 가져오기, 같은 ID는 덮어쓰기 확인)과 「내보내기」 탭(지금 유니버스를 JSON 파일로 내려받기).

- **알아 둘 한계:** ①은 새로 잡힌 「담당」 절에만 적용된다. 원래 사람 절(제목 "담당자"·"주 담당자"·"역할"·"이해관계자") 안의 "주 담당: 이름"은 켜도 v1대로(역할 "주 담당", 설명 "이름") 읽는다(limits L-55). 근거: 재검증 기본값 vs W8 전 210건 비교에서 12.9 밖 차이 0건(R13).
- **검증:** 고정 사례(tests/convert-w8·convert-r12·cr17-j 등)가 켠 항목마다 "읽혀야 할 것"과 "읽히면 안 되는 것"을 고정한다. 스위치를 모두 끄면 승인된 v1 동작이 되는 것이 설계 의도이고, 기본값 vs W8 전 비교는 review-2026-10-24-first-use.md R13에 있다(이번 승인으로 켠 뒤의 재비교는 T-40 재검증).
