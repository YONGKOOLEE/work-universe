## 1. 범용 데이터 모델 [2단계 제안]

### 1.1 설계 원칙

1. **유니버스는 업무에 붙는다**(00-context "유니버스 개념" 1). 소속과 조직은 유니버스 안의 사실(노드·연결·이벤트)이지 유니버스를 나누는 기준이 아니다.
2. **틀은 하나다**(R-07). 업무 성격별 필드를 스키마에 넣지 않는다. 업무 고유 정보는 노드의 자유 속성(키-값)과 태그로 담는다.
3. **바꾸지 않고 쌓는다.** 모든 변경은 이벤트로 남는다. 삭제는 숨김 표시만 한다(R-02 ②, R-14, R-05 흐름 변화).
4. **통합은 원본을 건드리지 않는다**(R-11 ⑤). 상위 유니버스는 하위 유니버스의 꼭지를 참조한다.

### 1.2 엔티티

| 엔티티 | 의미 | 키 | 필수 속성 | 선택 속성 | 제약 |
|---|---|---|---|---|---|
| **Universe** (유니버스) | 업무 하나, 또는 여러 유니버스를 모은 상위 단위 | `universe_id` | 이름, 단위 라벨(업무/팀/부서/본부/회사 또는 자유 입력), 작성 주체 | 설명, 태그 | 이름 누락 시 생성 거부(R-12 ②). 같은 이름+단위 중복 시 경고 |
| **Node** (노드) | 유니버스 안의 지식 단위 | `node_id` (유니버스 내 고유) | 유형, 라벨 | 자유 속성(키-값), 태그, 기간(시작·종료) | 유형은 1.3의 핵심 유형 중 하나. 삭제는 `숨김`만 가능 |
| **Edge** (연결) | 노드 사이의 관계 | `edge_id` | 출발 노드, 도착 노드, 관계 유형 | 유효 기간(시작·종료), 메모 | 같은 유니버스 안의 노드끼리만 연결(다른 유니버스와는 Ref·IdentityLink로 연결) |
| **Event** (이벤트) | 시점이 있는 사실과 변경 기록 | `event_id` | 시점, 유형, 대상(노드/연결 ID) | 변경 전후 값, 관련 사람, 메모, 근거 산출물 | 추가만 가능(수정·삭제 불가) |
| **Root** (꼭지) | 유니버스 자신을 나타내는 노드. 유니버스마다 1개 | `node_id` (유형=꼭지) | 유니버스 이름과 같은 라벨 | 요약 설명 | 유니버스를 만들 때 자동 생성. 숨길 수 없음 |
| **Ref** (꼭지 참조) | 상위 유니버스가 하위 유니버스의 꼭지를 포함함 | (상위 ID, 하위 ID) | — | 포함 시점 | 순환 참조 금지(A가 B를 포함하고 B가 A를 포함하는 경우 거부) |
| **IdentityLink** (동일성 연결) | 통합 유니버스에서 "서로 다른 유니버스의 두 노드가 같다"는 판정 | `link_id` | 두 노드(유니버스 ID+노드 ID), 판정 방식(`사번 자동`/`사람 확인`), 판정자 | 근거, 후보 점수 | 통합 유니버스에만 저장. 업무 노드는 `사람 확인`만 허용(v0.2 §6) |

### 1.3 핵심 노드 유형과 관계 유형

노드 유형(고정 6종):

| 유형 | 예 | 비고 |
|---|---|---|
| 꼭지 | 유니버스 자체 | 1.2 Root |
| 사람 | 담당자, 관계자 | 속성 `사번`(선택. 없으면 통합 때 확인 요청) |
| 업무 | 세부 업무, 절차, 과제 | 업무 유니버스의 하위 작업도 이 유형 |
| 산출물 | 문서, 링크, 보고서, 인수인계서 | 가상 제목과 요약만 저장 |
| 조직 | 팀, 부서 | 주로 조직관리 유니버스에서 트리로 사용 |
| 주제 | 키워드, 분류, 이슈 유형 | 유사 경험자와 반복 비효율 계산에 쓰는 공통 기준 |

관계 유형(고정 7종):

| 관계 | 의미 |
|---|---|
| 포함 | 꼭지 → 업무, 업무 → 하위 업무 |
| 수행 | 사람 → 업무. 유효 기간이 담당 기간이 됨 |
| 산출 | 업무 → 산출물 |
| 선후행 | 업무 → 업무 |
| 소속 | 사람 → 조직, 조직 → 조직. 유효 기간 있음 |
| 관련 | 모든 노드 → 주제 |
| 참조 | 모든 노드 → 모든 노드. 기타 연결 |

- 유형을 고정한 근거: 인사이트 계산(D-08)과 규칙 기반 초안(D-09)이 유형에 의존한다. 대신 업무별 고유 정보는 자유 속성과 태그로 담아 R-07을 지킨다.
- **개정안: 핵심 유형 + 하위 유형** [2단계 제안, 사용자 질문 "반드시 고정해야 하는지" 반영, 2026-09-30]
  - 사용자가 **하위 유형**을 자유롭게 추가할 수 있다. 예: 산출물 > 회의록·보고서, 사람 > 외부 협력사 담당자, 업무 > 점검·교육.
  - 하위 유형은 반드시 핵심 유형 하나에 속한다. 관계도 같은 방식이다. 예: 참조 > 검토함, 선후행 > 승인 후 진행.
  - 계산(D-08·D-09)은 핵심 유형으로 하고, 화면 표시·필터·범례는 하위 유형으로 한다.

| 대안 | 내용 | 판단 |
|---|---|---|
| ① 완전 고정 | 6개 노드 유형과 7개 관계 유형만 허용 | 계산은 가장 단순하지만, 업무 표현이 딱딱함 |
| **② 핵심 + 하위 유형 (권장)** | 계산용 핵심 유형은 고정하고, 표현용 하위 유형은 사용자가 추가 | 같은 틀(R-07)과 표현 자유를 함께 얻음. 비용은 편집 화면에 하위 유형 선택·추가 기능이 필요하다는 점(작은 기능) |
| ③ 완전 자유 | 유형을 사용자가 전부 정의 | 인사이트와 초안 규칙이 유니버스마다 달라져 R-07·R-05 조건을 지키기 어려움 → 포기 |

- **선택: ②** [사용자 선택, 2026-09-30. 조건: 나중에 확장할 수 있을 것]
- **확장 경로:**
  - **하위 유형 추가:** 데이터만 추가하면 된다. 코드 변경은 없다.
  - **핵심 유형 추가**(예: "고객", "시스템"): 유형 목록과 그 유형을 쓰는 계산 규칙(D-08·D-09)만 고치면 된다. 기존 데이터는 그대로 유지된다. 자주 쓰는 하위 유형을 핵심 유형으로 승격할 수도 있다.
  - **③(완전 자유)로 전환:** 가능하다. 다만 계산 규칙을 유형 대응표 기반으로 다시 짜야 한다.
- **확장을 위한 설계 조건:**
  - 핵심 유형 목록은 코드 한 곳(설정)에만 둔다.
  - 데이터에는 `핵심 유형`과 `하위 유형`을 따로 저장한다.
  - 모르는 유형의 데이터를 불러오면 오류로 멈추지 않고 "참조"·"기타"로 표시한다.

### 1.4 이벤트 유형

| 이벤트 | 기록 시점 | 쓰이는 곳 |
|---|---|---|
| 생성, 수정, 숨김 | 노드·연결을 만들거나 바꾸거나 숨길 때(자동 기록) | R-02 ②, 흐름 변화 |
| 담당 시작, 담당 종료 | 수행 연결이 생기거나 끝날 때 | R-03, 유사 경험자 |
| 인수인계 | 담당자가 교체될 때(보낸 사람, 받은 사람, 근거 산출물) | R-03, 반복 비효율 |
| 소속 변경 | 조직개편이나 발령 | R-14 |
| 메모 | 자유 기록(이슈, 결정 등) | R-03 근거, 흐름 변화 |

### 1.5 이력·삭제·중복·누락 규칙

- **이력:** 노드·연결의 현재 값은 마지막 이벤트까지 반영한 상태다. 수정 전 값은 `수정` 이벤트의 "변경 전" 값으로 남는다(R-02 ②).
- **삭제:** 사용자 삭제는 `숨김`으로 처리한다. 숨긴 노드는 기본 화면에서 빠지지만, 이력과 근거 참조는 유지된다. 실제 삭제는 "가상 데이터 초기화"로만 일어난다.
- **중복 판정(R-02 ④):**
  - 같은 유니버스에서 사람은 **같은 사번**이면 중복이다.
  - 사람 이외의 노드는 **같은 유형 + 같은 라벨**이면 중복이다. 라벨은 앞뒤 공백과 대소문자를 무시하고 비교한다.
  - 연결은 **같은 출발 노드·도착 노드·관계 유형이면서 유효 기간이 겹치면** 중복이다.
  - 어느 경우든 저장을 거부하고 기존 노드를 안내한다.
- **필수값(R-02 ③, R-12 ②):**
  - 유니버스: 이름, 단위 라벨, 작성 주체
  - 노드: 유형, 라벨
  - 연결: 양 끝 노드, 관계 유형
  - 사람의 사번은 필수가 아니다. 사번 없음은 R-11의 예외 사례로 다뤄야 하므로 입력 자체는 허용하고 경고만 표시한다.
- **소속 누락(R-14):** 소속 연결이 없는 기간은 "미기재"로 표시하고, 업무 이력은 그대로 이어서 보여 준다.

### 1.6 사람과 조직의 위치

- 업무 유니버스의 "사람" 노드는 그 업무에 관여한 사람을 나타낸다. 소속은 필요할 때만 `소속` 연결로 적는다.
- 조직관리 유니버스는 사람·조직 노드와 소속 변경 이벤트를 **자신의 업무 데이터로** 가진다(00-context "유니버스 개념" 2).
- 업무 유니버스와 조직관리 유니버스의 사람은 **통합할 때 사번으로만** 대응시킨다.
- 프로토타입에서는 조직관리 유니버스가 다른 유니버스의 기준 데이터가 되어 값을 검증하거나 덮어쓰지 않는다. 이 역할은 v0.2 §12-2에 따라 R-09로만 다룬다.

### 1.7 데이터량·보관·인덱스 후보

- **데이터량** [임시 가정 DA-1]:
  - 가상 인물 20~30명, 팀 유니버스 3개(A·B·C)와 조직관리 유니버스 1개
  - 유니버스당 노드 수십~200개, 조직개편 이벤트 2~3회
  - 출처: 정의서 v0.1 §6의 가상 데이터 원칙. 사용자 승인 "진행"(2026-09-30).
  - 업무 내용이나 인물 정보가 더 필요하면 개발자가 사용자에게 요청한다(사용자 요청, 2026-09-30). 요청할 항목은 3단계 R-13 작업에 적는다.
- **보관:** 프로토타입에서는 해당 없음(01-requirements 4절).
- **인덱스 후보:** 파일·브라우저 저장소라 별도 인덱스는 해당 없음. 불러올 때 메모리에 아래 조회 표를 만든다.
  - 사번 → 사람 노드
  - (유형, 정규화 라벨) → 노드
  - 노드 → 이벤트 목록(시간순)
  - 주제 → 노드 목록

## 2. 팀 유니버스 구성 방식 (RQ-4 결정) [2단계 제안]

| 대안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 꼭지 모음 | 팀 유니버스는 자기 노드 없이 업무 유니버스들의 꼭지만 참조한다 | 개념이 깔끔함. 업무 이력이 업무 유니버스에만 존재 | 팀 공통 자료(팀 공지, 팀 규칙)를 둘 곳이 없음. 업무 유니버스를 여러 개 먼저 만들어야 해서 시연 준비가 무거움 |
| B. 직접 생성 | 팀이 유니버스 하나를 만들고, 업무는 그 안의 "업무" 노드로 둔다 | 만들기 쉬움. 시연 데이터 작성이 가벼움 | 업무 하나 = 유니버스 하나(v0.2 §1)와 어긋남. 나중에 업무를 떼어 내기 어려움 |
| **C. 혼합 (선택)** | 모든 유니버스는 **자기 노드를 가질 수 있고, 동시에 다른 유니버스의 꼭지를 참조할 수도 있다** | A와 B가 같은 틀의 두 사용법이 됨. 팀은 직접 생성으로 시작하고, 나중에 업무 유니버스를 분리해 참조로 바꿀 수 있음. 통합(R-11)도 같은 방식(참조)으로 표현됨 | 화면에서 "내 노드"와 "참조된 노드"를 구분해 보여 줘야 함 |

- **결정 D-02: C(혼합).**
  - 사용자가 "지금 고민"이라고 한 질문이 틀 선택이 아니라 **사용 방식 선택**이 되도록 만드는 결정이다. 어느 쪽으로 쓰든 같은 틀 안에서 표현된다.
  - 시연 데이터는 두 방식을 모두 보여 준다(4절 사례): A팀은 업무 유니버스를 참조하는 방식(A 사용법), B팀은 직접 생성 방식(B 사용법)으로 만든다.
- 미검증 전제: 참조와 직접 노드가 섞여도 탐색 화면(R-01)이 이해하기 쉬운가. 검증은 3단계 R-08 대리 검증 때 관찰한다.

## 3. 통합 방식 (R-11) [2단계 제안]

| 대안 | 내용 | 판단 |
|---|---|---|
| 복사 병합 | 하위 유니버스의 노드를 새 유니버스에 복사하고 합친다 | 포기. 원본과 사본이 따로 놀아, 하위 유니버스를 수정해도 반영되지 않음 |
| **참조 + 동일성 연결 (선택)** | 새 부서 유니버스는 하위 꼭지를 `Ref`로 참조하고, 합칠 노드 쌍만 `IdentityLink`로 저장한다. 화면은 불러올 때 합쳐진 모습을 계산해 보여 준다 | 원본이 바뀌지 않음(R-11 ⑤). 하위 수정이 자동 반영됨. 사람의 판정 기록이 남음 |

**결정 D-03: 참조 + 동일성 연결.** 통합 절차는 다음과 같다.

1. 사용자가 하위 유니버스(A·B·C)를 선택하고, 새 유니버스 이름과 단위("부서")를 입력한다.
2. **사람 대응:**
   - 사번이 같고 이름도 같으면 `사번 자동`으로 연결한다.
   - 사번은 같은데 이름이 다르면 **충돌**, 사번이 없으면 **사번 없음**이다. 두 경우 모두 확인 목록에 올리고 자동으로 판단하지 않는다(R-11 ③).
3. **업무 후보:**
   - 규칙 기반: 주제 공유 수, 라벨 유사도, 산출물 유형 공유로 후보 점수를 매긴다.
   - LLM 설정이 있으면 후보 이유를 문장으로 덧붙인다(역할 c).
   - 사용자가 후보마다 "같음/다름"을 확정해야만 `IdentityLink`가 생긴다(R-11 ②).
4. 확인하지 않은 항목이 남아 있어도 통합 유니버스는 저장할 수 있다. 미확인 항목은 "확인 대기"로 표시된다.
5. 통합 유니버스는 일반 유니버스와 같은 탐색 화면(R-01)과 인사이트(R-05)를 쓴다(R-11 ④).

## 5. 실행 형태와 기술 결정

### 5.1 실행 형태 (D-05) [2단계 제안]

제약 조건:
- 심사위원 PC는 알 수 없고, 최소 절차로 실행돼야 한다(A-1).
- 메일로 제출한다.
- 제출물에 키가 없어야 한다(A-2).
- 개발은 개인 PC에서 Claude Max로 한다.

| 대안 | 심사위원 실행 절차 | 호환성 | 운영·유지보수 | 비용 | 판단 |
|---|---|---|---|---|---|
| 1. Python + Streamlit 로컬 웹 (v0.1 후보) | Python 설치 → 패키지 설치 → 명령 실행 | OS와 무관하지만 설치 부담이 큼 | 코드 작성이 쉬움 | 무료 | 포기: A-1(최소 절차) 위반 가능성이 큼 |
| 2. Windows 실행 파일(Python 패키징) | 더블클릭 | Windows만 가능. 백신 경고 가능성. 파일이 커서 메일 첨부 제한 위험 | 빌드가 번거로움 | 무료 | 포기: OS 제한, 메일 용량 위험 |
| **3. 정적 웹 앱(HTML·JS 한 폴더, 브라우저로 열기) (선택)** | 압축 해제 → `index.html` 더블클릭 | 최신 브라우저(Chrome, Edge 등)만 있으면 OS 무관. 인터넷 없이도 동작(라이브러리를 함께 넣음) | 서버 없음. 초기화·내보내기가 쉬움 | 무료. LLM 사용 시 API 크레딧만 | 선택 |
| 4. 웹 호스팅 URL | 링크 클릭 | 가장 쉬움 | 호스팅 관리 필요 | 무료~소액 | 보류: 링크 제출 허용 여부가 **미확인**. 허용되면 3과 같은 파일을 그대로 올리는 보조 수단으로 씀 |

**결정 D-05: 3. 정적 웹 앱.** 사용자 승인 "진행", 2026-09-30.

- **선택 이유:** 심사위원 PC 환경을 알 수 없고(A-1), 메일로 제출하므로, 설치 없이 OS와 관계없이 더블클릭 한 번으로 실행되는 방식이 이 프로젝트 조건에 가장 맞는다. 그래프 탐색 화면(R-01)도 브라우저가 가장 잘 그린다.
- **CORS와의 관계:** CORS는 선택 이유가 아니라, 이 방식을 택했을 때 지켜야 하는 **제약**이다(P-1).
- **포기한 이점:** Python에 비해 데이터 처리 라이브러리가 적다. 프로토타입 규모(DA-1)에서는 문제되지 않는다고 판단한다.

이 결정에는 미검증 전제가 두 가지 있다. 3단계의 첫 작업에서 실측한다.

| 전제 | 확인한 내용 | 영향 | 검증 방법 |
|---|---|---|---|
| **P-1** 더블클릭 실행 | `file://`로 연 HTML이 JS 모듈을 불러오면 CORS 오류가 난다(MDN "JavaScript modules", 확인일 2026-09-30) | 빌드 결과를 **모듈을 쓰지 않는 번들 1개(또는 HTML 1개에 인라인)**로 만들어야 함 | 빈 화면 + 그래프 라이브러리만 넣은 최소 파일을 Chrome·Edge에서 더블클릭으로 연다 |

**P-1 실측 결과 (T-01, 2026-09-30): 통과.** Chrome 154.0.8037.58과 Edge 154.0.4258.37에서 `dist/index.html`(일반 `<script src="app.js">`, 모듈 없는 IIFE 번들)을 `file://`로 열었을 때 그래프 표시, 클릭 상세, 노드 추가가 동작했다. 인터넷 요청을 모두 막은 상태에서도 동작했고 외부 요청은 0건이었다. 자동 점검(`tools/browser-check.mjs`) 뒤 사용자가 탐색기에서 직접 더블클릭해 확인했다. 대안 K-3(인라인 단일 HTML → 로컬 서버)은 쓰지 않는다. 상세: `docs/tech-record.md` 5절.

**P-1 해결 방안** (사용자 질문 "우회나 출처 지정으로 해결 가능한지" 반영, 2026-09-30):

- **오류를 일으키는 방식을 쓰지 않는다.**
  - 모듈 스크립트(`type="module"`)와 `fetch()`로 로컬 파일을 읽는 방식을 쓰지 않는다.
  - 대신 일반 스크립트 파일(또는 HTML 안에 넣은 스크립트)과 JS로 감싼 샘플 데이터를 쓴다.
  - 사용자가 고른 JSON 파일은 파일 선택 창으로 읽는다. 이 방식은 CORS 대상이 아니다.
  - 일반 스크립트가 `file://`에서 동작하는지는 **P-1 실측으로 확인**한다.
- **"출처 지정"은 해당 없다.** CORS 허용 출처는 **서버가** 응답 헤더로 지정한다. 더블클릭 실행에는 서버가 없으므로 지정할 곳이 없다.
- **브라우저 보안 옵션 끄기는 쓰지 않는다.** 실행 옵션으로 로컬 파일 접근을 허용하는 우회는 심사위원 PC에 적용할 수 없고, 보안상 권하지 않는다.
- **최후 대안:** 제출물에 작은 로컬 서버 실행 파일을 넣는다. 실행 절차가 늘어나므로(A-1), 위 방식이 실패할 때만 쓴다.
- **P-2(Claude API)의 CORS는 별개다.** Anthropic 서버가 허용 여부를 정하고, 브라우저 직접 호출용 헤더가 있다(비공식 자료). 이 호출은 개발 PC·영상에서만 필요하며, 실패하면 D-07b(로컬 중계)로 대신한다. 심사위원 PC는 LLM을 호출하지 않으므로 이 문제와 무관하다.
| **P-2** 브라우저에서 Claude API 직접 호출 | `anthropic-dangerous-direct-browser-access: true` 헤더로 가능하다고 비공식 자료(Simon Willison, 2024-08-23)에 나온다. Anthropic 공식 문서에서는 **미확인** | 실패하면 개발 PC·영상용으로만 작은 로컬 중계 프로그램이 필요(대안 D-07b) | 개발 PC에서 테스트 키로 호출 1회. `file://` 출처에서도 되는지 함께 확인 |

### 5.2 저장 (D-06) [2단계 제안]

| 대안 | 판단 |
|---|---|
| **브라우저 저장소 + JSON 가져오기·내보내기 + 초기 가상 데이터 내장 (선택)** | 설치가 필요 없고 초기화가 쉬움(01-requirements 4절 "초기 상태 복귀") |
| 로컬 파일 직접 쓰기 | 브라우저 보안상 파일을 자동으로 쓸 수 없고 매번 사용자 확인이 필요 → 포기 |
| 로컬 DB·서버 | D-05와 충돌 → 포기 |

- 저장 단위는 유니버스 1개 = JSON 문서 1개다. 구성은 `universe`, `nodes`, `edges`, `events`, `refs`, `identity_links`다.
- 미검증 전제 **P-3:** `file://`에서 브라우저 저장소(localStorage 또는 IndexedDB)가 유지되는가. 브라우저마다 다를 수 있다. 검증은 P-1과 같은 최소 파일로 저장 → 새로고침 → 확인한다. 유지되지 않으면 "세션 동안만 유지 + 내보내기 안내"로 축소한다.
- **P-3 실측 결과 (T-01, 2026-09-30): 통과.** Chrome·Edge(위 P-1과 같은 버전)에서 `localStorage`에 저장한 노드가 새로고침 뒤에도, 브라우저를 정상 종료했다 다시 연 뒤에도 유지됐다. 저장소 접근이 막히면 `W-STORAGE` 배너가 뜨고 샘플을 읽기 전용으로 연다. 대안 K-4(세션 유지 + 내보내기)로 축소하지 않는다.
  - 관찰: 저장 직후 몇 초 안에 브라우저를 강제 종료하면 마지막 변경이 디스크에 기록되지 않을 수 있다. 시연 안내에 내보내기를 권한다.

### 5.4 LLM 연결부 계약 (D-07) [2단계 제안]

- **입력:** 작업 종류(`초안`/`인사이트 설명`/`업무 후보 이유`), 근거 목록(노드·이벤트 ID와 그 내용).
  - 근거 목록에는 가상 데이터만 들어간다.
  - 근거로 고른 것만 보내고, 전체 유니버스는 보내지 않는다.
- **출력:** 항목 목록. 각 항목은 {문장, 근거 ID 목록}이다. 생성 방식(`LLM`/`규칙 기반`)과 실패 사유를 함께 돌려준다.
- **공급자:** 화면·기능 코드는 이 계약만 사용한다(R-15).
  - `없음`
  - **`사전 생성`(기본, CR-1 2026-09-30):** 개발 중 Claude Code가 작성한 결과 파일(출력 계약과 같은 형식)을 불러온다.
    - 조회 키는 (작업 종류, 대상 노드 ID, 근거 ID 목록)이다.
    - 파일에 없는 요청이 오면 규칙 기반으로 응답한다. 새로 입력한 데이터가 이 경우에 해당한다.
    - 근거 목록이 달라졌으면 낡은 결과로 보고 버린다(K-9).
  - `Claude API`(P2, 선택)
  - `사내 LLM`(P2)
- **생성 방식 표시:** `사전 생성` / `LLM` / `규칙 기반` 세 가지다.
- **검증과 오답 처리:**
  - LLM이 준 근거 ID가 실제로 없거나 비어 있으면, 그 항목은 버리고 규칙 기반 결과로 대체한다. 대체한 항목에는 표시를 남긴다.
  - 응답 형식이 깨졌거나 시간이 초과되면 전체를 규칙 기반으로 전환하고 원인을 표시한다(R-04 ③).
- **키 보관:**
  - 키는 설정 화면에서 입력하고 **개발 PC 브라우저 저장소에만** 둔다. 파일과 저장소 코드에는 넣지 않는다.
  - 제출 전 점검: 제출 폴더에서 키 형식 문자열을 검색해 0건이어야 한다(R-15 ③).
- **모델 선택:** 2단계에서 정하지 않는다. 3단계에서 Claude API 모델 목록과 요금을 확인한 날짜와 함께 기록한다.
- **대안 D-07b:** P-2가 실패하면 개발 PC에서만 실행하는 작은 로컬 중계 프로그램을 둔다. 이 프로그램은 제출물에 넣지 않는다.

### 5.5 인사이트 계산 규칙 (D-08) [2단계 제안]

모든 인사이트는 LLM 없이 계산하고, LLM은 설명 문장만 쓴다.

| 인사이트 | 규칙 | 데이터 부족 조건 |
|---|---|---|
| **유사 경험자(P0)** | 선택한 업무와 주제·산출물 유형·라벨 토큰을 공유하는 다른 업무를 찾아 점수화한다. 그 업무를 `수행`한 사람을 점수순으로 보여 주고, 근거로 공유 주제와 업무 노드를 붙인다. 현재 담당자는 제외한다 | 주제·산출물 연결이 없는 업무 |
| 밀집/공백 | 조직(또는 하위 유니버스)별 활성 업무 수와 수행 인원 수를 집계한다. 담당자가 없는 업무(공백)와 1인이 N개 이상을 맡은 경우(밀집)를 표시한다. N은 화면에서 조정하며 기본값은 정하지 않고 3단계 데이터로 정한다 | 수행 연결이 없는 유니버스 |
| 반복 비효율 | ① 같은 업무에서 인수인계 이벤트가 2회 이상인데 이후 인수인계가 이전 인수인계서를 `참조`하지 않음. ② 같은 주제의 메모·인수인계가 서로 다른 업무 2곳 이상에서 반복됨. 근거 이벤트를 목록으로 보여 준다 | 인수인계·메모 이벤트가 2건 미만 |
| 흐름 변화 | 기간(월·분기)별 이벤트 수와 업무·사람 변화를 시간 슬라이더로 보여 준다 | 이벤트 시점 범위가 한 기간 이하이거나, 마지막 입력 이후 기간 |

### 5.6 규칙 기반 인수인계 초안 (D-09) [2단계 제안]

아래 항목은 고정이며, 항목마다 근거를 찾는 규칙이 정해져 있다. 근거가 없으면 "이력 부족"으로 표시하고 내용을 만들지 않는다.

| 항목 | 근거를 찾는 규칙 |
|---|---|
| 업무 개요 | 꼭지 또는 업무 노드의 설명 |
| 세부 업무·주기 | 포함 연결, 속성 |
| 선후행 | 선후행 연결 |
| 산출물 | 산출 연결 |
| 관계자 | 업무에 연결된 사람. 보내는 사람은 제외 |
| 최근 이슈 | 최근 메모 이벤트 N건 |
| 이전 인수인계 | 인수인계 이벤트와 근거 산출물 |
| 유사 경험자 | D-08 결과. 받는 사람이 물어볼 사람 |

- LLM 설정이 있으면 같은 근거로 문장만 다듬는다(5.4).

### 12.1 공통 규칙

| 항목 | 규칙 |
|---|---|
| 파일 단위 | 유니버스 1개 = JSON 문서 1개(`schema_version` 포함). 샘플도 같은 형식이며, JS 변수로 감싸서 넣는다(P-1) |
| 스키마 버전 | `"1.0"`. 불러올 때 버전이 다르면 경고하고 읽기 전용으로 연다 |
| ID | 문자열. 유니버스는 `U-`, 노드는 `N-`, 연결은 `L-`, 이벤트는 `E-`, 동일성 연결은 `I-` 접두어를 쓴다. 새 ID는 접두어 + 무작위 영숫자 8자리로 만든다. 샘플은 읽기 쉬운 ID(예: `U-A1`, `N-001`)를 써도 된다. 노드·연결·이벤트 ID는 유니버스 안에서 고유하다 |
| 전역 참조 | `"<universe_id>/<local_id>"`(예: `"U-A1/N-003"`). 다른 유니버스를 가리킬 때와 근거 ID에 쓴다 |
| 날짜 | 업무 시점은 `YYYY-MM-DD`다. 월 단위만 알면 1일로 적는다. 입력 시각은 ISO 8601 날짜·시각(시간대 포함)이다 |
| 문자열 | 라벨은 1~100자다. 중복 비교는 앞뒤 공백을 제거하고 영문 소문자로 바꾼 값으로 한다 |
| 숨김 | `hidden: true`. 삭제 필드는 두지 않는다(D-04) |

### 12.2 유니버스 문서 구조

```json
{
  "schema_version": "1.0",
  "universe": { },
  "nodes": [ ],
  "edges": [ ],
  "events": [ ],
  "refs": [ ],
  "identity_links": [ ]
}
```

**universe**

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | 필수(자동) | `U-…` |
| `name` | string | 필수 | 1~100자 |
| `level` | string | 필수 | `업무`/`팀`/`부서`/`본부`/`회사` 또는 자유 입력 |
| `owner` | string | 필수 | 작성 주체(사람 또는 조직 이름) |
| `description` | string | 선택 | |
| `tags` | string[] | 선택 | |
| `root_node_id` | string | 필수(자동) | 꼭지 노드 ID |
| `subtypes` | `{core_type, name}[]` | 선택 | 사용자 하위 유형 목록(1.3 ②) |
| `is_sample` | boolean | 필수(자동) | 초기화 대상 여부 |
| `created_at` | datetime | 필수(자동) | |

**nodes[]**

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | 필수(자동) | `N-…` |
| `core_type` | enum | 필수 | `root`(꼭지), `person`(사람), `work`(업무), `artifact`(산출물), `org`(조직), `topic`(주제) |
| `subtype` | string | 선택 | `universe.subtypes`에 있는 이름. 없는 이름은 저장 거부 |
| `label` | string | 필수 | |
| `description` | string | 선택 | |
| `attrs` | object(string → string 또는 number) | 선택 | 업무 고유 정보(예: 주기) |
| `tags` | string[] | 선택 | |
| `period` | `{start, end}` | 선택 | 날짜. `end`가 없으면 진행 중 |
| `emp_no` | string | 선택 | `person`만 가능. 샘플은 `V-` + 숫자 4자리 |
| `hidden` | boolean | 필수(기본 false) | |
| `created_at`, `updated_at` | datetime | 필수(자동) | |

**edges[]**

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | 필수(자동) | `L-…` |
| `source`, `target` | string | 필수 | 같은 유니버스의 노드 ID |
| `core_type` | enum | 필수 | 아래 허용 조합 표 참고 |
| `subtype` | string | 선택 | |
| `period` | `{start, end}` | 선택 | 담당·소속 기간 |
| `note` | string | 선택 | |
| `hidden` | boolean | 필수(기본 false) | |
| `created_at` | datetime | 필수(자동) | |

관계 유형과 허용 조합은 다음과 같다. 목록 밖의 조합은 저장을 거부한다(`E-PAIR`).

| `core_type` | 의미 | 허용 조합(출발 → 도착) |
|---|---|---|
| `contains` | 포함 | root → 꼭지 이외 모든 노드, work → work |
| `performs` | 수행 | person → work |
| `produces` | 산출 | work → artifact |
| `precedes` | 선후행 | work → work |
| `belongs_to` | 소속 | person → org, org → org |
| `relates_to` | 관련 | 꼭지 이외 모든 노드 → topic |
| `references` | 참조 | 꼭지 이외 노드 → 꼭지 이외 노드 |

**events[]**

공통 필드:

| 필드 | 형식 | 필수 | 설명 |
|---|---|---|---|
| `id` | string | 필수(자동) | `E-…` |
| `type` | enum | 필수 | 아래 유형 표 참고 |
| `occurred_at` | date | 필수 | 업무 시점 |
| `recorded_at` | datetime | 필수(자동) | 입력 시각 |
| `source` | enum | 필수(자동) | `user`/`sample`/`system` |
| `payload` | object | 유형별 | 아래 표 참고 |
| `note` | string | 선택 | |

유형별 `payload`:

| `type` | 뜻 | `payload` |
|---|---|---|
| `created`, `hidden` | 생성, 숨김 | `{target_kind: "node" 또는 "edge", target_id}` |
| `updated` | 수정 | `{target_kind, target_id, before: {…바뀐 필드}, after: {…}}` |
| `assign_start`, `assign_end` | 담당 시작·종료 | `{person_id, work_id}` |
| `handover` | 인수인계 | `{work_id, from_person_id, to_person_id, artifact_id?, previous_handover_id?}` |
| `affiliation_change` | 소속 변경 | `{person_id, from_org_id?, to_org_id?}`. 없는 값은 "미기재"(R-14) |
| `memo` | 메모 | `{target_id?, topic_ids?: []}` |

- `previous_handover_id`는 반복 비효율 규칙 ①에서 "이전 인수인계서를 참조했는가"를 판정할 때 쓴다(D-08).

**refs[]**

`{child_universe_id, added_at}`. 부모 문서에 저장한다. 순환이면 거부한다(`E-CYCLE`).

**identity_links[]** (통합 유니버스만)

| 필드 | 형식 | 설명 |
|---|---|---|
| `id` | string | `I-…` |
| `a`, `b` | 전역 참조 | 같다고 판정할 두 노드 |
| `kind` | enum | `person`/`work` |
| `method` | enum | `emp_no_auto`(사번 자동. 사람만 가능) / `human`(사람 확인) |
| `status` | enum | `pending`(확인 대기) / `confirmed` / `rejected`. 거부한 쌍은 다시 제안하지 않는다 |
| `score` | number | 선택. 후보 점수 |
| `reason` | string | 선택. 규칙 기반 또는 사전 생성 이유 |
| `decided_by`, `decided_at` | string, datetime | `human`일 때 필수 |

### 12.3 사전 생성 결과 파일 (CR-1)

```json
{
  "schema_version": "1.0",
  "generator": "Claude Code (개발 시 작성)",
  "generated_at": "2026-10-…T…+09:00",
  "items": [
    {
      "task": "handover",
      "target": "U-A1/N-001",
      "evidence_ids": ["U-A1/N-003", "U-A1/E-004"],
      "sentences": [
        { "text": "…", "evidence_ids": ["U-A1/N-003"] }
      ]
    }
  ]
}
```

- `task`: `handover`(초안) / `insight_explain`(인사이트 설명) / `work_candidate_reason`(업무 후보 이유)
- 조회 키: (`task`, `target`, 정렬한 `evidence_ids`). 키가 맞지 않으면 낡은 결과로 보고 규칙 기반을 쓴다(K-9).
- 문장의 `evidence_ids`가 실제 데이터에 없으면 그 문장은 버린다(D-07).

### 12.7 시스템 구조

**계층과 의존 방향**

화살표는 "호출한다"를 뜻한다. 위에서 아래로만 호출한다.

```
┌──────────────────────────── ui (화면 8종, 5.3) ─────────────────────────────┐
│ 사용자 입력 → 명령 호출 / 결과·오류 코드 → 한국어 메시지 표시             │
└───────────────┬──────────────────────────────┬──────────────────────────────┘
                ▼                              ▼
        app (명령·상태)                    view (합성 뷰)
  addNode / updateNode / hide /     유니버스 + refs(재귀) + identity_links
  createUniverse / merge /          → 화면·규칙이 쓰는 하나의 그래프(읽기 전용)
  generateHandover / insight                   │
        │        │         │                   │
        ▼        ▼         ▼                   ▼
     model     store     rules ◄────────── (view를 입력으로 받음)
  검증·이벤트  브라우저    초안 8항목(D-09), 인사이트(D-08), 업무 후보(D-03)
  (순수 함수)  저장·가져오기          │
                ·내보내기             ▼
                                   llm 연결부(D-07)
                           none / pregen / claude_api / internal
                                      │
                                      ▼
                             근거 ID 검증 → 결과 + 생성 방식
```

**모듈 책임**

| 모듈 | 책임 | 의존 | 테스트 |
|---|---|---|---|
| `model` | 12.2 스키마, 검증(12.5 코드), 명령 적용 → (새 문서, 이벤트) | 없음(순수 함수) | Node 단위 테스트 |
| `store` | 12.4 키로 읽기·쓰기, JSON 가져오기·내보내기, 샘플 초기화 | 브라우저 저장소 | 수동. 저장소 불가 시 `W-STORAGE` |
| `view` | refs를 재귀로 펼치고 identity_links로 노드를 합쳐 읽기 전용 그래프 생성. 노드마다 출처(전역 참조) 유지 | model | Node 단위 테스트 |
| `merge` | 통합 절차(3절): 사번 대응, 업무 후보 점수, 확인 목록 생성 | model, view | Node 단위 테스트 |
| `rules` | 초안·인사이트·후보 계산. 모든 결과 항목에 근거 ID | view | Node 단위 테스트 + 정답 표 |
| `llm` | 공급자 선택, 사전 생성 조회, 근거 ID 검증, 규칙 기반 대체 | rules 결과 | Node 단위 테스트(사전 생성·대체) |
| `app` | 명령 흐름 조립, 현재 유니버스·선택 노드 상태 | 위 모듈 전부 | 시나리오 체크리스트 |
| `ui` | 화면, 그래프 라이브러리 연결, 오류 코드 → 메시지 | app, view | 시나리오 체크리스트 |

- 규칙: `model`, `view`, `merge`, `rules`, `llm`은 브라우저 기능(DOM, 저장소)을 쓰지 않는다. 그래야 Node에서 테스트할 수 있다.

**핵심 흐름 3가지**

1. **자료 저장(R-02):**
   1. ui 입력 → `app.addNode`
   2. `model` 검증. 실패하면 오류 코드를 ui에 돌려준다.
   3. 성공하면 새 문서와 `created` 이벤트가 생긴다.
   4. `store`에 저장한다.
   5. `view`를 다시 계산하고 그래프를 갱신한다.
2. **인수인계 초안(R-03·R-04·R-15):**
   1. ui에서 업무·보내는 사람·받는 사람을 고른다.
   2. `rules`가 8개 항목과 근거 ID를 만든다. 근거가 없는 항목은 "이력 부족"이다.
   3. `llm`이 공급자에 따라 사전 생성 결과를 조회하거나 API를 호출하고, 근거 ID를 검증한다. 실패하면 규칙 기반 문장을 쓴다.
   4. ui가 항목별 문장, 근거 링크, 생성 방식을 표시한다.
3. **통합(R-11):**
   1. ui에서 하위 유니버스들을 선택한다.
   2. `merge`가 사번 자동 연결(`confirmed`)과 확인 목록(`pending`)을 만든다.
   3. 새 부서 유니버스 문서를 만든다(`refs`와 `identity_links`만 가짐).
   4. `store`에 저장한다.
   5. 사용자가 확인하면 `status`를 바꾸고 이벤트를 기록한다.
   6. `view`를 다시 계산한다.
