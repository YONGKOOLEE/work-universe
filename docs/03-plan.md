## 1. 제안 구조와 작업 방식

### 1.1 디렉터리 구조 (제안)

```
work-universe/
├─ docs/            계획 문서(현재)
├─ inputs/          입력 자료(읽기 전용)
├─ app/             소스
│  ├─ index.html
│  ├─ src/
│  │  ├─ model/     엔티티·검증·이벤트·유형 설정 (D-01, D-04)
│  │  ├─ store/     브라우저 저장소·가져오기·내보내기·초기화 (D-06)
│  │  ├─ rules/     인수인계 초안·인사이트 규칙 (D-08, D-09)
│  │  ├─ merge/     꼭지 참조·동일성 연결 (D-02, D-03)
│  │  ├─ llm/       연결부: 없음 / Claude API (D-07)
│  │  └─ ui/        화면 8종 (02-design 5.3)
│  ├─ data/         가상 샘플(JS로 감싼 데이터) + 정답 표
│  └─ vendor/       그래프 라이브러리(오프라인 번들)
├─ tests/           model·rules·merge 단위 테스트
├─ tools/           빌드, 제출 점검(키 검색, 실데이터 체크리스트)
└─ dist/            제출용 빌드 결과(저장소에 넣지 않음)
```

### 1.2 설정·실행·테스트·린트·배포 (제안)

| 항목 | 제안 | 확정 시점 |
|---|---|---|
| 개발 도구 | 개발 PC에 Node.js LTS와 Git 설치(버전 **미확인**) | T-01 |
| 모듈·빌드 | 소스는 JS 모듈로 작성하되(테스트 편의), 빌드 결과는 **모듈 없는 단일 스크립트**로 만든다(P-1). 번들러 후보는 esbuild, 또는 빌드 없이 일반 스크립트로 작성 | T-01 결과로 결정 |
| 개발 실행 | 빌드 후 `dist/index.html`을 더블클릭한다. 심사위원과 같은 방식이다 | T-01 |
| 테스트 | ① model·rules·merge는 Node 내장 테스트 러너로 단위 테스트. ② 화면은 R-ID별 수동 시나리오 체크리스트(01-requirements 5절)로 확인 | T-03부터 |

### 1.3 역할 (사용자 결정 반영, 2026-09-30)

조력자는 계획의 필수 담당에서 제외한다. 사용자 판단: "코딩에서 별로 중요하지 않다". 조력자는 무엇이든 도울 수 있으므로 선택적 지원으로만 둔다.

| 사람 | 담당 |
|---|---|
| 개발자(사용자) | 모든 T-ID의 구현·검증. Claude Code(Claude Max) 사용. 가상 데이터 작성(T-04, T-13)과 영상·소개자료(T-16)도 Claude Code와 함께 수행 |
| 조력자(선택) | 가상 데이터 뼈대 정보 제공(7.2, 사용자 결정 2026-09-30). 깨끗한 PC 실행 테스트에 PC 제공(T-15). 영상·소개자료 검토. 없으면 1.4의 대체 방법을 쓴다 |
| 대리 검증자(RA-1) | R-08 첫 사용 관찰(T-14). 프로젝트를 모르는 사람 |

### 1.4 조력자 제외에 따른 대체

| 원래 역할 | 대체 |
|---|---|
| 가상 데이터 작성 | 개발자가 Claude Code로 생성한다. 입력은 7절 Q2의 간단한 정보 |
| R-06 교차 점검 | 도구 점검(키·실명 패턴 검색)과 개발자 체크리스트로 대신한다. 교차 확인자가 없는 위험은 수용한다(K-7) |
| 깨끗한 PC 실행 테스트 | 다른 PC(가족·지인)가 가장 좋다. 없으면 개발 PC에서 새 브라우저 프로필, 인터넷 차단, 다른 브라우저로 확인한다. 다른 OS 확인이 빠지는 위험은 수용한다(K-3) |
| 영상·소개자료 | 개발자가 만든다. 영상은 대본을 먼저 쓰고 촬영한다 |

### 7.1 변경 요청 CR-1: 사전 생성 방식 [승인됨: "cr-1 방식을 승인", 2026-09-30. 01·02·03 반영 완료]

- **의미 정리:**
  - 실행 중인 프로그램이 Claude Code(개발 세션의 Claude)를 부를 수는 없다.
  - 대신 **개발 중에** Claude Code(Claude Max 구독)가 샘플 데이터를 보고 (a) 초안 문장, (b) 인사이트 설명, (c) 업무 후보 이유를 미리 써 둔다. 이것을 "사전 생성 결과" 파일로 앱에 넣는다.
  - 앱은 연결부(R-15)의 새 공급자 `사전 생성`으로 이 파일을 읽는다.
- **장점:** API 비용이 0이다. 심사위원 PC에서도 LLM 품질의 문장이 보인다. 키 관리 문제가 없다.

  - 미리 만든 데이터에만 결과가 있다. 시연 중에 추가한 자료(R-02)는 반영되지 않고, 그 부분은 규칙 기반으로 표시된다.

### 9.1 확정 결정

1. **D-05:** 정적 웹 앱(JavaScript)으로 만들고, 압축을 풀어 `index.html`을 더블클릭하면 실행된다. 빌드 결과는 모듈 없는 단일 스크립트다.
2. **D-01·D-04:** 유니버스·노드·연결·이벤트·꼭지 모델. 핵심 유형 6종·관계 7종과 사용자 하위 유형을 쓴다. 변경은 이벤트로 쌓고 삭제는 숨김으로 처리한다.
3. **D-02·D-03:** 유니버스는 직접 노드와 꼭지 참조를 함께 가진다. 통합은 참조와 동일성 연결로 하고, 사람은 사번으로 자동 연결하고, 업무는 사람이 확정한다.
4. **D-07(CR-1):** LLM 문장은 개발 중 Claude Code로 사전 생성한다. 새 데이터에는 규칙 기반 문장을 쓴다. 연결부는 공급자 4종이며 근거 ID를 검증한다.
5. **PL-2:** M1(MVP 종단 흐름)을 마치면 중간 제출본을 확보한다. 범위 축소 순서는 승인됐다.

### 9.4 구현 세션 시작 프롬프트

구현 세션을 시작하기 전에 사용자가 할 일은 두 가지다.

