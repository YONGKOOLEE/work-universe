# CR-12 초안 — 1차 제출에서 "실제로 써도 될 만큼"까지 완성하기

- 문서: CR-12 v0.2 · 상태: **approved(2026-10-13, 사용자 "승인 하는데 일정은 폐기 … 기능동결날짜도 폐기 진행사항에 따라 flexible 하게")** · 작성 2026-10-13
- 승인 조건: 3절의 날짜 일정과 기능 동결 날짜(10-23 추천)는 **폐기**. 구현 순서와 범위 축소 순서만 남기고, 동결 시점은 진행 상황에 따라 사용자가 정한다
- 요청 근거(사용자 표현, 2026-10-13): "1차 제출물을 뛰어넘은 실제로 써도 될만큼의 완성도", "소프트웨어 개발 및 산출물 제출이 1차까지 … 1차에 모든 프로그램을 완료해야될거 같은데", 범위 확대 "진행"
- 사용자 제공 사실: **1차 제출 마감 2026-10-30.** 2차는 발표만 한다(개발 없음).
- 진단 근거: `docs/limits.md`(L-21 확정자, L-24 저장, L-26 찾기 등), 조력자 의견(2026-10-12, decisions-pending 9절), 여섯 번째 검토 C11-3(숨긴 노드 되살리기)
- **이 CR이 다루지 않는 것:** 서버·로그인·권한·여러 사람 동시 사용·사내 연동·실제 LLM 연결(자리만 유지, P2 그대로). 실제 회사 배포가 아니라 "한 사람이 매일 써도 불편하지 않은 완성도"가 목표다.
- 승인 전에는 01·02·03을 고치지 않는다. 승인되면 "반영할 곳"대로 고치고 `docs/.status`의 `doc_changes`에 기록한다.

## 1. 왜 필요한가

| 영역 | 지금 | 매일 쓰면 막히는 장면 |
|---|---|---|
| 인수인계서 | 화면 안에서 초안·확정만 된다 | 받는 사람에게 문서로 건네거나 인쇄할 수 없다 |
| 이슈 관리 | 메모 분류(이슈·진행 중·해결됨)는 있지만 해결 표시는 새 메모를 직접 써야 하고, 미해결만 모아 볼 곳이 없다 | 업무당 1년 30~50건(조력자 답)이 쌓이면 무엇이 남았는지 모른다 |
| 실수 복구 | 숨긴 노드를 되살릴 수 없다 | 잘못 숨기면 다시 만들어야 하고 이력이 끊긴다 |
| 데이터 안전 | 이 브라우저 저장소에만 있다(L-24). 내보내기는 있지만 권하지 않는다 | 브라우저 정리·PC 교체 때 통째로 잃는다 |
| 찾기 | 이름만 찾는다(L-26) | "점검표" 같은 낱말이 설명·속성에만 있으면 못 찾는다 |
| 기록 주체 | 확정자가 늘 "사용자(이 브라우저)"(L-21) | 누가 확정했는지 남지 않는다 |
| 배치 | 흐름 정렬은 시제품 버튼 | 조력자 두 명이 같은 지적(유형별 정리·방향) |

## 2. 변경 항목 (추천 순서 = 구현 순서)

### A. 인수인계서 내보내기 (새 R-19)

| 항목 | 내용 |
|---|---|
| 요구 | 초안과 확정한 인수인계서를 파일로 내려받고 인쇄할 수 있다 |
| 인수 기준 ① | 초안·확정본 화면의 「내려받기」 → 항목·문장·근거 목록이 담긴 파일 1개(.html, 더블클릭으로 열림, 외부 파일 없음). 파일 이름은 "날짜-대상-인수인계서" |
| 인수 기준 ② | 「인쇄」 → 인쇄용 화면(브라우저 인쇄로 PDF 저장 가능). 그래프·버튼은 빠지고 A4 세로에 맞는다 |
| 인수 기준 ③ | "이력 부족"·"해당 없음" 표시와 생성 방식(사전 생성·규칙 기반)이 파일에도 그대로 남는다(지어내지 않음) |
| 오류 | 저장소 쓰기는 없으므로 실패 경로는 브라우저 내려받기 차단뿐 → 안내 문구 |
| 결정(D-21) | 형식은 **HTML 파일 + 브라우저 인쇄**. .docx는 라이브러리 추가(크기·라이선스)가 필요해 하지 않는다. 마크다운·텍스트는 표가 깨져 기본으로 두지 않는다 |

### B. 미해결 이슈 보기와 해결 표시 (새 R-20)

| 항목 | 내용 |
|---|---|
| 요구 | 해결되지 않은 이슈·진행 중 메모를 모아 보고, 한 번에 "해결"로 표시한다 |
| 인수 기준 ① | 유니버스 개요와 업무 상세에 「미해결 n건」 → 목록(날짜·업무·내용). 묶음 화면에서는 하위 유니버스 것까지 |
| 인수 기준 ② | 목록의 「해결로 표시」 → 같은 대상·주제의 "해결됨" 메모가 새로 생기고 목록에서 빠진다. 원래 메모는 바뀌지 않는다(이력 추가만, D-04) |
| 인수 기준 ③ | 인수인계 초안의 「진행 중」 항목과 같은 판정을 쓴다(지금 규칙: 같은 대상에 이후 "해결됨" 메모가 있으면 닫힘) |
| 결정(D-22) | 상태 변경은 **새 메모 이벤트**로 기록한다. 스키마는 바꾸지 않는다(12.2 memo 범주 그대로) |

### C. 숨긴 노드 되살리기와 백업 권유 (새 R-21)

| 항목 | 내용 |
|---|---|
| 인수 기준 ① | 개요에 「숨긴 노드 n개」 → 목록 → 「되살리기」. 연결·이력은 숨기기 전 그대로 보인다. 이력에 "되살림"(updated, hidden true → false)이 남는다 |
| 인수 기준 ② | 마지막 내보내기 뒤 바뀐 것이 있고 7일이 지났거나 변경이 30건을 넘으면 머리글에 「내보내기를 권합니다」 한 줄. 닫으면 다음 기준까지 숨김 |
| 결정(D-23) | 되살리기는 **새 이벤트 종류를 만들지 않고** updated(before/after hidden)로 기록한다. 기준값(7일·30건)은 상수 한 곳 |

### D. 찾기 넓히기와 작성자 이름 (새 R-22)

| 항목 | 내용 |
|---|---|
| 인수 기준 ① | 찾기에 「설명·속성까지」 선택(기본 켬). 이름 일치가 먼저, 설명·속성 일치는 그 아래에 어디서 찾았는지와 함께 |
| 인수 기준 ② | 설정에 「작성자 이름」(이 브라우저에 저장). 확정자·이력 추가의 기록 주체에 쓰인다. 비면 지금처럼 "사용자(이 브라우저)" |
| 결정(D-24) | 작성자 이름은 로그인이 아니다(누구나 바꿀 수 있음)를 화면과 limits에 적는다 |

### E. 흐름 정렬 결정 반영 (설계 결정만, D-25)

- 사용자가 스크린샷(`.tmp/shots/*-20*`)을 보고 정한다: ① 버튼으로만 유지(추천) ② 업무 유니버스는 흐름 정렬을 기본으로 ③ 버림.

### F. 변환기 실제 문서 대응 (T-21 조건부 재포함)

- 조력자 가상화 업무정의서가 **10-20까지** 오면 그 문서로 규칙을 고친다(02 12.9.2 D-P1~P7 중 필요한 것만). 안 오면 T-21은 지금처럼 제외.

### G. 대사 확인 → 인수인계서 「산출」 연결 (조력자 지적, 02 5.6.1)

- 추천: **바꾸지 않는다.** 연결 메모("인수인계 초안 확정")와 상세 문구로 "이 업무의 인수인계 기록"임을 드러낸다. 바꾸면(산출 → 참조) 확정 흐름·사전 생성·초안 근거·테스트가 함께 바뀌어 회귀 위험이 크다.

## 3. 순서 (날짜 없음 — 사용자 결정 2026-10-13 "일정은 폐기", 동결은 진행에 따라 유연하게)

- 구현 순서: A(T-23) → B(T-24) → C(T-25) → D(T-26) → E 반영(T-27) → F(T-21, 조력자 샘플이 왔을 때만) → 점검·일곱 번째 전체 검토(T-28).
- 마감은 2026-10-30(사용자 제공). 기능 동결 시점은 정하지 않고, 진행 상황을 보며 사용자가 정한다. 동결 뒤에는 결함 수정과 사람 몫(화면 확인, 다른 PC·메일(T-15), 대본·소개자료·영상(T-16))만 한다.
- 항목마다 구현 → 검토 → 수정 → 재검증 → 제출 압축(9/9)을 거친다. **언제든 마지막 통과 압축을 그대로 낼 수 있다.**
- 시간이 모자라면 **아래 순서로 뺀다**(먼저 뺄 것부터): F → D → C의 백업 권유 → C의 되살리기 → B → A. T-28(점검·전체 검토)은 빼지 않는다.
