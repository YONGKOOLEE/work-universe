# CR-17 — 처음 사용 점검에서 나온, 승인 문서를 바꿔야 하는 세 가지

- 문서: CR-17 v0.1 · 상태: **draft(사용자 승인 전)** · 작성 2026-10-24 · 근거: docs/first-use-2026-10-24.md(처음 보는 사용자 역할 3명, FU-21·FU-22·FU-23)
- 원칙: 승인 문서(01·02·03)와 다르게 구현해야 하는 것만 모았다. 나머지 지적(FU-1~FU-20)은 승인된 요구(R-08 처음 사용 길, R-26 인수인계 위험 등) 안의 문구·길 찾기·표시라 이 CR 없이 반영 중이다.
- **답이 없으면:** 아무것도 바꾸지 않는다(지금 동작 유지). A는 승인 즉시 반영할 수 있게 브랜치에 준비만 해 둔다.

## A. 단추·창 이름의 「유니버스」 → 「업무 지도」 (FU-21, 세 명 모두 지적)

| | 지금 | 바꾸면 |
|---|---|---|
| 머리글 | 「새 유니버스」「유니버스 묶기」, 고르기 칸 「유니버스 선택」 | 「새 업무 지도」「업무 지도 묶기」「업무 지도 선택」 |
| 시작 화면 | 「새 유니버스 만들기」 | 「새 업무 지도 만들기」 |
| 그 밖 | 「노드 추가」 | 「사람·업무·문서 추가」(또는 「항목 추가」) |
| 그대로 | 제품 이름 「업무 UNIVERSE」, data-testid, 저장 형식·내보내기 파일 안의 낱말, 승인 문서의 용어 "유니버스"(문서는 "업무 지도(유니버스)"로 병기) | |

- 왜 지금: D-34는 "단추 이름은 1차 후(점검 460여 항목·따라 하기 이름 결합)"로 미뤘다. 처음 보는 사용자 3명이 모두 「유니버스」·「업무 지도」가 섞인 것을 첫 혼란으로 꼽았다. 점검은 대부분 testid로 찾으므로, 글자로 찾는 항목과 따라 하기 문구만 고치면 된다(어림: 점검 20~30곳, 따라 하기 문구 10곳 안팎).
- 바뀌는 문서: 02 D-34(뒤집기), 5.3 화면 표의 단추 이름, 01 R-08 ⑤의 "단추 이름은 그대로", limits L-51(이중 표기 해소), 실행안내·대본·소개자료의 단추 이름.
- 위험: 낮음~중간(글자 바꿈. 점검을 전부 다시 돌려야 함). 되돌리기 쉬움(문자열 표 한 곳).
- 추천: **승인**. 첫인상에서 가장 많이 걸린 것이고, 동결 전에 해야 영상·소개자료를 다시 찍지 않는다.

## B. 「유사 경험자」를 「대신할 수 있는 사람」에 가깝게 (FU-22, 팀장 역할)

- 지적: ① 「대사 확인」을 9월까지 직접 하던 사람이 "2025 행사에서 같은 주제"라는 엉뚱한 이유로 나옴 ② 1위가 실제 사람이 아닌 역할 이름(「운영 담당」) ③ 「2026 행사」는 「2025 행사」 담당자가 있는데 "데이터 부족".
- 원인(규칙 rules/insight.js similarExperts): 이 규칙은 "기준 업무와 주제·산출물 유형을 공유하는 **다른** 업무를 한 사람"만 센다. 같은 업무를 예전에 직접 한 사람(이전 담당)은 그 업무로는 세지 않고, 다른 업무를 통해서만 나온다. 이름 낱말이 같아도 주제·산출물을 공유하지 않으면 후보가 되지 않는다. 역할 이름 노드도 사람과 똑같이 센다.
- 바꾸면: ① 맨 위에 **「직접 해 본 사람」**(기준 업무의 이전 담당 — 수행 연결이 끝난 사람, 기간 표시) 묶음 ② 역할 이름 노드는 아래 「사람 미확인(역할 이름)」 묶음으로 따로 ③ 주제·산출물 공유가 없어도 **이름 낱말이 같은 업무**(예: 「2025 행사」↔「2026 행사」)는 낮은 점수로 후보에 넣고 이유를 "이름에 같은 낱말 「행사」"로.
- 바뀌는 문서: 01 R-05 ① 인수 기준, 02 5.5 유사 경험자 규칙·D-08, 사전 생성 문장(유사 경험자 설명 지문이 바뀌어 다시 써야 함 — 개발 중 Claude로 다시 작성).
- 위험: 중간(규칙·사전 생성 지문·점검 기대값). 반나절~1일.
- 추천(2회차 반영해 올림): **①②③ 승인**. 2회차 파트장 역할도 업무 4개 중 3개에서 "없음"을 받고 "여기서 믿음이 크게 떨어졌다"고 했다(FU-40). ③은 낮은 점수 + "이름에 같은 낱말 — 확인 필요" 표시로 오탐 위험을 줄인다.

## C. 새 업무 지도 창의 「첫 업무」에 설명·절차·주의사항 칸 (FU-23 일부, 실무자 역할)

- 지적: 만들기 창의 「설명」은 지도 설명이라 업무에 들어가지 않는다. 절차·주의사항은 만든 뒤 「수정」→「+ 속성 추가」에서 이름을 정확히 쳐야 한다(FU-16으로 권장 항목 단추는 반영 중).
- 바꾸면: 첫 업무 칸에 「설명」「절차(한 줄에 하나)」「주의사항」 세 칸(선택). 비우면 지금과 같다.
- 바뀌는 문서: 02 5.3 유니버스 생성 행(첫 업무 S-1~S-3), 01 R-12.
- 위험: 낮음. 반나절 이내.
- 추천: **승인**(내 업무로 시작하는 사람의 첫 10분이 줄어듦). 다만 FU-16 반영 뒤 2회차 점검에서도 같은 막힘이 나오면 하는 것으로 미뤄도 됨.

## D. 받는 사람 입구 — 시작 화면 넷째 갈래 「인수인계를 받았어요」 (FU-28, 2회차 받는 신입 역할)

- 지적: 첫 화면 세 갈래와 따라 하기가 모두 넘기는(만드는) 쪽 말투라 받는 사람이 갈 길이 없다.
- 바꾸면: 넷째 카드 「인수인계를 받았어요」 → 예시 지도에서 받는 사람 = 나로 고른 초안 + 미해결(진행 중인 일) + 공백 경고를 한 화면 순서로 보여 주는 짧은 따라 하기(3단계, 고치기 단계 없음).
- 바뀌는 문서: 01 R-08 ①(세 갈래 → 네 갈래), 02 5.3 시작 행·D-29, 03 T-32.
- 위험: 낮음~중간(시작 화면 1366×768 높이, 따라 하기 점검). 반나절.
- 추천: **보류(1차 후)**. 문구로 먼저 메움(첫 카드 "넘기는 쪽도 받는 쪽도", 5단계 "연습용"). 2차 발표에서 "받는 사람 화면"이 필요하면 그때.

## E. 인수인계 초안에 「받는 사람이 맡을 범위·담당 공백」과 「최근 바뀐 것」 (FU-39, 받는 신입 역할)

- 지적: 지도 전체 초안이 "세 업무 모두"를 받는 사람이 하는 것처럼 쓴다. 실제로 받는 사람이 맡은 것은 한 업무이고 나머지 둘은 지금 담당 공백인데 초안에 없다. 최근 바뀐 규칙(마감 5→3영업일)이 이력 맨 밑에만 있다.
- 바꾸면: 초안 항목 둘 추가 — 「받는 범위와 담당 공백」(받는 사람이 지금 수행 중인 업무 / 지금 담당이 없는 업무 — 밀집·공백과 같은 기준), 「최근 바뀐 것」(최근 90일 속성 수정 이력: "마감: 5영업일 → 3영업일(2026-10-01)").
- 바뀌는 문서: 01 R-03 초안 항목 표, 02 5.6 초안 항목·D-?, 사전 생성 문장 2항목 × 시연 조합 추가(개발 중 Claude로 작성), 점검 기대값(항목 수 10 → 12).
- 위험: 중간(규칙·사전 생성·점검). 1일.
- 추천: **「받는 범위와 담당 공백」만 승인**(오해를 직접 막고, 이미 있는 공백 판정 재사용). 「최근 바뀐 것」은 FU-15로 이력 글이 읽기 쉬워졌으니 1차 후.

## F. 「관계자·연락처」에 협업자 포함 (FU-38, 실무자 역할 1·2회차 모두)

- 지적: 법무 검토 담당·외부 사이트 담당·요청 부서처럼 수행자가 아닌 협업자를 초안의 관계자로 넣을 길이 없다(규칙이 「수행」 연결만 센다). 조직(회계팀)을 이어도 계속 「이력 부족」.
- 바꾸면: 업무에 「참조」로 이은 사람·조직도 관계자로 센다(문장: "법무 검토는 윤가온(참조)에게"). 사람의 「연락처」 속성을 함께.
- 바뀌는 문서: 01 R-03 관계자 항목 인수 기준, 02 5.6 관계자 규칙, 사전 생성 문장 지문(관계자 항목), 「채우려면」 문구.
- 위험: 낮음~중간(규칙 한 곳, 지문 1~2항목). 반나절.
- 추천: **승인**(두 실무자 역할이 같은 곳에서 막힘, 내 업무로 쓸 때 가장 먼저 비는 칸).

## G. 「업무 개요」와 「세부 업무·절차」 중복 문장 (FU-19, 실무자 역할 1·2회차)

- 원인: 대상 업무에 절차·사용 시스템이 있으면 세부 항목의 대상 업무 줄에도 설명이 다시 들어간다(rules/handover.js).
- 바꾸면: 세부 항목의 대상 업무 줄에서는 설명을 빼고 절차·시스템만.
- 바뀌는 문서: 02 5.6 세부 항목 규칙(문장 한 줄), 사전 생성 지문(대상이 업무인 조합만).
- 위험: 낮음. 2시간.
- 추천: **승인**.

## H. 키 없이 「Claude API」를 고르면 사전 생성 문장으로 대체 (FU-54, 3회차 IT 심사위원)

- 지금: 「설정」에서 Claude API를 고르고 키를 넣지 않으면 공급자가 없어 **규칙 기반**으로 대체된다(03 T-36 오류 처리 "키 없음 → 규칙 기반 + 원인"). 같은 예시 지도인데 기본값(사전 생성)보다 문장이 못해 보여 "AI를 고르니 오히려 나빠졌다"로 읽힌다.
- 바꾸면: 키가 없거나 실시간 호출이 실패하면 **사전 생성 → 규칙 기반** 순으로 대체(사전 생성 문장도 지금처럼 근거·지문 검사). 띠: "키가 없어 미리 받아 둔 문장(사전 생성)으로 보여 줍니다".
- 바뀌는 문서: 03 T-36 오류 검증 칸, 02 5.4 대체 순서, 점검 기대값(CR-15 블록의 「규칙 기반으로 대체함」 항목).
- 위험: 낮음(연결부 한 곳). 2~3시간.
- 추천: **승인**.

## I. 확정할 때 「담당을 받는 사람으로 넘기기」 (FU-55, 3회차 문서로 시작한 실무자)

- 지금: 인수인계를 확정하면 인수인계서(산출물)와 인수인계 이력이 남지만, 현재 담당(수행 연결)은 그대로다. 받는 사람은 연결 없이 떠 있다.
- 바꾸면: 확정 확인 창에 선택 칸 「담당도 넘기기(보내는 사람의 수행을 오늘로 끝내고 받는 사람의 수행을 내일부터 시작)」, 기본 꺼짐. 켜면 같은 묶음 명령으로 연결 기간을 바꾼다(되돌리기·편집 되감기 대상).
- 바뀌는 문서: 01 R-03 ③(확정 결과), 02 5.6·D-?, 03 T-?(새 작업), 점검.
- 위험: 중간(데이터를 바꾸는 명령, 되감기·이력과의 관계). 반나절.
- 추천: **1차 후**. 확정 결과 안내에 "담당은 「연결 수정」에서 기간으로 넘깁니다" 한 줄로 먼저 메움(승인 없이 가능 — 반영 중).

## J. 업무정의서 변환 보강 켜기 (FU-53, 3회차 문서로 시작한 실무자) — **준비됨, 기본은 꺼 둠**

- 경위: 3회차 반영 때 변환 보강을 "12.9 규칙 안의 낱말 보강"으로 보고 바로 켰으나, 재검증(R11-1, docs/review-2026-10-24-first-use.md)에서 일부가 승인된 12.9.1 v1·D-P3·D-P6과 다르게 동작한다는 지적을 받아 **스위치(CONVERT_RULES.cr17j) 뒤로 옮기고 기본값을 승인된 동작으로 되돌림**.
- 기본으로 켜 둔 것(승인 범위 안): 제목 낱말(「담당」류 → 이해관계자·역할 절, 「관련·참고·첨부 문서」 → 산출물·문서 절), 담당 절의 이름을 **역할 사람 노드**로(연결 없음), 관련 문서 → 산출물 노드(꼭지가 담음, 괄호는 설명), 「작성:」「작성 부서:」 줄을 「작성자:」와 같게(값 그대로 — D-P6), 「업무정의서:」류 접두어를 업무 이름에서 떼기, 미리 보기 이름 수정이 업무에도.
- 승인하면 켤 것(스위치): ① 「주 담당·담당·정」으로 적힌 사람 → 업무 하나짜리 문서에서 `performs`(D-P3의 근거 기준 완화) ② 이름이면 하위 유형 없는 사람 ③ 관련 문서 → 업무 `references`, 괄호 경로 → 속성 「위치」 ④ 「작성자:」 값에서 조직 낱말만 골라 작성 주체·날짜는 작성일(**D-P6 "변경 없음" 뒤집기**) ⑤ 개요 첫 문장 → 업무 설명, 개요의 분명한 주기·마감 구절 → 속성(오탐 위험 — "매년 개정되는 세법" → 주기 「매년」 같은 경우를 줄이는 조건 필요) ⑥ 인수인계 초안 「산출물·문서 위치」가 「참조」 문서도 읽기(R-03).
- 바뀌는 문서: 02 12.9.1 표·D-P3·D-P6, 01 R-15 변환 인수 기준, R-03(⑥).
- 위험: 중간(①④는 승인된 결정을 뒤집음, ⑤는 오탐). 켜는 데 10분, 문서 반영 1시간.
