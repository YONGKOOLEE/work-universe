# CR-23 문서로 더하기 — 업무 하나에 문서를 붙여 지도를 키운다

- 문서: CR-23 v0.1 · 상태: **구현됨(브랜치 `cr23-doc-attach`, 메인 합치기 전)** · 날짜: 2026-10-28
- 승인 문서(00~03)는 고치지 않았다. 메인이 합칠 때 01(R-ID)·02(모듈 표·화면 글)·03(T-ID)에 반영한다.
- 저장 형식(문서 JSON 스키마)은 **바꾸지 않았다**.

## 1. 배경

- 조력자(가상 업무로 시험하는 동료)의 말: "업무 하나 등록한 다음에 문서들 쭉쭉 올리면 실제 지도에 반영되는 그런 모습들을 보고싶어서".
- 지금까지: 「가져오기」(ui/import.js)는 문서 하나 → **새** 업무 지도 하나만 만든다. 「글로 추가」(ui/text-add.js)는 지도에 더하지만 「A가 B를 맡는다」 같은 짧은 문장(4000자·60문장) 전용이라 회의록·매뉴얼에서는 0개를 읽는다.
- 조력자가 준 가상 문서 4개를 `tests/fixtures/doc-attach/`에 두었다(PDF에서 복사한 글이라 표가 칸 구분 없이 공백으로만 이어져 있다 — 이것이 실제 입력 모양이다). 1·2: 회의록(결정사항·후속 조치 표 「과제 담당 기한」·미결/추적), 3: 월정산 매뉴얼, 4: 프로모션 이력 메모(날짜 글머리표 이력).

## 2. 사용자 승인 (원문 인용)

- 2026-10-27~28, 사용자: "둘 포함 B까지 진행한느게 나아보인느데", "그러면 지금 진행하고" (이 기능 = B). 변경 요청 번호는 CR-23 「문서로 더하기」.
- 이 문서의 범위 밖(별도 제안): PDF·한글·워드 파일 직접 읽기, 같은 업무의 할 일 수정(이미 있는 업무의 마감·담당 갱신), 묶은 지도에서의 사용.

## 3. 화면 흐름

입구 세 곳 — ① 「사람·업무·문서 추가」 묶음의 「문서로 더하기」(「표로 추가」「글로 추가」 옆) ② 업무 카드 「⋯」 메뉴의 「이 업무에 문서 더하기」(그 업무가 대상으로 미리 골라져 열림) ③ 「무엇을 할까요?」 찾기(낱말: 문서·회의록·매뉴얼·메모·올리기·업로드·붙이기·반영·문서 더하기).

| 순서 | 화면 | 동작 |
|---|---|---|
| ① | 어느 업무에 붙일까요? | 이 지도의 업무 목록. 기본값 = 고른 카드의 업무, 없으면 업무가 하나일 때 그것, 여럿이면 「업무를 고르세요」 |
| ② | 문서를 넣으세요 | 붙여 넣기 칸 + 파일 열기(.md, .txt). .pdf·.hwp·.hwpx·.docx 등을 고르면 읽지 않고 「PDF·한글·워드 파일은 글을 복사해 붙여 넣어 주세요」 |
| ③ | 읽어 보기 | 규칙으로 읽는다(키 없이). 키가 있으면 옆에 「Claude로 읽기」(규칙 결과에 Claude가 더 찾은 항목을 보탠다), 없으면 「「설정」에서 키를 넣으면 Claude가 읽습니다」 |
| ④ | 미리 보기 | 문서 1개 · 할 일 업무 n개(담당 역할·마감·상태) · 메모 n건(분류·날짜·글) · 읽지 못한 줄 · 만들지 않은 절. 체크 상자로 고른다. 글이나 대상 업무가 바뀌면 「다시 읽으세요」(저장 잠김) |
| ⑤ | 지도에 더하기 | `app.applyBatch` 한 번 — 한 번에 전부 아니면 전무, 되감기 한 점 |
| ⑥ | 끝 | 창이 닫히고 대상 업무 카드가 열리며 알림 「문서 1·업무 n·메모 n 더함 — 되돌리려면 지도 관리 → 편집 되감기」(메모가 있으면 「메모는 되감아도 남습니다」 한 줄 추가) |

묶은 지도(팀·부서)에서는 단추 대신 「문서로 더하기: 팀·업무 지도를 열어 넣으세요」 한 줄, 읽기 전용·편집 되감기 중에는 열리지 않는다(글로 추가·표로 추가와 같은 기준).

## 4. 규칙 읽기 (rules/doc-attach.js, DOM 없음)

원문에 있는 것만 읽고, 확신이 없는 줄은 만들지 않고 「읽지 못한 줄」로 보인다. 낱말·상한은 파일 맨 위 상수(`DOC_ATTACH_WORDS`·`DOC_ATTACH_LIMITS`) 한 곳에 있다.

| 만드는 것 | 읽는 모양 | 저장되는 모양 |
|---|---|---|
| **문서 항목** (산출물 1개) | 이름 = 첫 줄(「제목:」·대괄호 머리 정리, 100자 상한). 설명 = 「문서 날짜」(일시·작성일 줄, 없으면 제목의 날짜) · 「작성 부서」(작성부서 줄) + 「결정」(제목에 결정·결론·의결·합의가 든 절의 ①②③·번호·문장) + 「이력」(날짜로 시작하는 글머리표 줄, 12줄까지·줄당 90자), 설명 상한 2000자 | 대상 업무 → 문서 `references` (PAIR_RULES: work→artifact 허용) |
| **할 일 업무** | 머리줄이 {과제·조치·할 일·작업·실행 과제·업무} + {담당·책임·주관} + {기한·일정·마감·시점} 낱말을 모두 가진 짧은 줄(파이프 표·탭 표·공백뿐인 표). 그 아래 줄부터 **그 절의 끝까지**가 행. 공백뿐인 표는 머리줄이 「과제 담당 기한」 순서일 때만: 줄 끝의 날짜 꼴 = 기한, 그 바로 앞 낱말 = 담당, 나머지 앞부분 = 과제 이름. 파이프·탭 표는 머리줄의 칸 순서를 따른다 | 대상 업무 → 업무 `contains`, 속성 「마감」(날짜 하나면 `YYYY-MM-DD`, 범위·「월 말」·「이후」는 원문 그대로) |
| **담당 역할** | 담당 칸을 「/」「,」로 나눈 이름. 이미 지도에 같은 이름 사람이 있으면 그 항목에 잇고, 없으면 사람(하위 유형 「역할」, 같은 묶음에서 등록)을 만든다. 같은 이름은 하나 | 역할 → 업무 `performs` (배치 명령 `assign` = 수행 연결 + 담당 시작 이력, 오늘부터) |
| **메모** | 제목에 {미결·미확정·확인 필요·질문}이 든 절의 문장 → 범주 `issue`. 제목에 {유의·주의·추적·리스크·위험}이 든 절의 문장 → `caution`. 「말한 주체: 문장. 문장.」 줄은 뒤 문장에도 주체를 붙인다. 앞에 「[문서명] 」 출처. 날짜 = 문서 날짜(오늘 이후면 오늘), 없으면 오늘 | 대상 업무의 메모 이벤트(배치 명령 `addMemo`) |
| 그 밖의 절 | 만들지 않는다(주제 노드 남발 금지). 참석·부서 나열로 사람을 만들지 않는다. 만들지 않은 절의 제목만 미리 보기에 보인다 | — |

같은 이름이 이미 있을 때(`text-extract`의 `docCandidates`·`findMatch` 방식): 업무·산출물·사람은 새로 만들지 않고 그 항목에 잇는다(연결은 `skipDup`, 담당은 이미 담당 중이면 건너뜀). 같은 이름이 둘 이상이면 새 항목으로 만들고 알린다. 대상 업무와 같은 이름·대상의 상위 업무(`contains` 순환)는 막는다. 같은 메모(대상·글이 같음)는 「이미 있음」으로 처음부터 체크하지 않는다.

**기한 지남**: 기한의 마지막 날이 오늘이나 문서 날짜보다 앞이면 「기한 지남」 표시 + 처음 체크 해제(사람이 체크하면 들어간다). 「2017. 3월 말」은 그 달 마지막 날, 범위는 끝 날짜로 본다.

**상한**: 글 20만 자, 할 일 25, 역할 25, 메모 25(합쳐서 한 번에 76행 — applyBatch 행 상한 100 안).

### 메모 범주를 issue·caution으로만 쓰는 이유

- `resolved`(해결됨)는 같은 대상의 열린 메모를 닫는다(rules/issues.js `openMemos`). 문서가 앱 안의 미해결을 지워 버리면 안 된다.
- `in_progress`·`issue`는 매주 점검의 「열린 항목」으로 센다. 그래서 「미결」 절만 `issue`(정말 열린 일), 정보·주의 성격(유의·추적)은 열린 항목으로 세지 않는 `caution`으로 둔다.
- 따라서 이 기능은 `resolved`·`in_progress`를 **만들지 않는다**(단위 시험으로 확인).

## 5. 명령 추가 (model/commands.js `applyBatch`)

저장 형식은 그대로이고 배치에 명령 두 개를 더했다. 기존 명령·시험은 바뀌지 않았다.

- `{op:'addMemo', row, input:{target_id, occurred_at, category?, note}}` — `addEvent`로 `memo` 이벤트를 만든다. `target_id`는 노드 id 또는 같은 묶음 앞 행의 `'@행'`. 대상이 없으면 그 행 오류 → 전체 되돌림. 결과에 `memos`(이벤트 목록)가 추가됨.
- `{op:'addSubtype', aux:true, input:{core_type, name}}` — 하위 유형(「역할」)을 같은 묶음에서 등록한다. 이미 있으면 건너뛴다(오류 아님). 설정 변경이라 이벤트는 남지 않는다.

## 6. Claude 읽기 (llm/ai-doc-attach.js)

- 키가 있을 때만 단추가 보인다. 글로 추가의 Claude 읽기(`llm/ai-extract.js` 검증, `llm/connector.js`의 `extractTextAsync`)를 **그대로** 부른다 — 호출·인용 검증을 새로 만들지 않았다. 인용이 보낸 덩어리에 없는 행은 버려지고, 연결의 근거 문장에 부정·나열 표시가 있으면 확인 필요로 처음부터 체크하지 않는다.
- 문서가 글로 추가 상한(4000자)을 넘으면 `chunkDocument`가 줄·절 제목 경계에서 상한 이하 덩어리로 나눠(절 제목만 덩어리 끝에 남지 않게, 한 줄이 상한보다 길면 자름) 차례로 보낸다(최대 8덩어리). `mergeProposals`가 같은 유형·이름을 하나로 합치고 지도와 다시 맞댄다.
- 규칙 계획과 같은 이름(문서·할 일·담당)의 Claude 항목은 `dedupeAiProposal`이 뺀다. Claude가 더 찾은 새 업무는 대상 업무 아래(`contains`)에 잇고 지도 중심에는 잇지 않는다. 처음에는 모두 체크하지 않는다.
- 실패(전체)하면 규칙 결과를 그대로 보이고 이유 한 줄(「Claude 읽기 실패: … — 규칙으로 읽은 결과를 보여 줍니다」). 일부 덩어리만 실패하면 나머지 결과만 보이고 알린다.
- **실제 API 응답으로는 시험하지 못했다(미확인).** `llm/fake-client.js` 방식의 가짜 공급자로만 시험했다.

## 7. 한계

- **PDF·한글·워드 파일을 직접 읽지 못한다.** 글을 복사해 붙여 넣어야 한다(`.md`·`.txt`만 파일로 연다, 2MB까지).
- **공백뿐인 표는 휴리스틱이다.** 머리줄이 「과제 담당 기한」 순서이고 줄 끝이 날짜 꼴이며 담당이 한 낱말(「/」·「,」로 이은 것 포함)일 때만 읽는다. 과제 이름 끝이 담당처럼 보이거나 담당이 두 낱말(「서비스 사업」)이면 그 행은 읽지 못한 줄로 남는다. 표 모양이 여러 줄에 걸치면 읽지 못한다.
- 절 제목은 「1. 제목」(앞 번호 다음 번호일 때만)·「## 제목」·「■ 제목」·「【제목】」 꼴만 안다. 한글·워드의 다른 번호 체계(가. 나.)는 절로 나누지 않는다.
- **메모는 되감기로 지워지지 않는다**(편집 되감기는 사용자 이력인 메모를 남긴다 — model/rewind.js 기존 한계). 알림에 그 말을 넣었고, 필요 없으면 「해결로 표시」로 닫는다. 문서 항목·업무·역할·연결은 되감기로 숨겨진다.
- 이미 지도에 있는 업무에는 마감·설명을 갱신하지 않는다(연결만 잇는다).
- Claude 읽기는 실제 응답으로 확인하지 못했다.
- 세금·법규·약관 같은 판단은 하지 않는다.
