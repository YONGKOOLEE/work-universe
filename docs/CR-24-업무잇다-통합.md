## 1. 목적과 범위

담당자가 바뀌어도 업무의 맥락이 끊기지 않게 한다는 목적은 같다. 두 결과물을 **하나의 프로그램**으로 합친다.

- **본체 = 업무잇다.** 업무 등록, 문서 등록·분석(PDF·HWPX·TXT), 반영 미리보기·승인, 업무 한눈에 보기, 타임라인, 회의록, AI 업무 검색, 인계 8단계·스냅샷, 데이터 옮기기를 업무잇다 화면·동작대로 둔다.
- **확장 = 업무 유니버스 지도.** 업무잇다에 쌓인 업무·사람·문서·조직이 모이면 그 관계를 지도(그래프)로 넓게 보고, 지도에서도 고친다.
- 공동 제출, 하나의 제품. 이름은 「업무잇다」(나중에 바꿀 수 있음).

## 3. 구조

```
itda/                         ← 통합 제품(업무잇다 소스를 바탕으로 함)
  src/lib, pages, components  업무잇다 화면·저장소(AppState)
  src/universe/               지도: AppState → 유니버스 문서(파생) · 지도 화면 · 지도 편집 명령
  src/ai/                     키 방식 AI(유니버스 llm 모듈 재사용) + 규칙(업무잇다 Mock + 유니버스 규칙)
app/src/{model,view,rules,merge,llm}  유니버스 순수 모듈 — itda가 그대로 불러 씀(시험 그대로 유지)
```

- **D24-1 데이터는 하나.** 저장은 업무잇다 AppState 하나(localStorage). 지도는 AppState에서 **파생한 유니버스 문서**(메모리에서만 만듦)를 유니버스 view·그래프 코드로 그린다. 지도에서 고치면 AppState를 고치는 명령으로 바뀌고, 지도는 다시 파생한다. 두 저장소를 맞추는 일은 없다.
- **D24-2 파생 규칙(대응표).**

| AppState | 지도(유니버스) |
|---|---|
| Work | 업무 항목(work). 상태·유형은 속성 |
| Work.parentId | 포함(contains) |
| Work.relatedIds | 참조(references) |
| Work.nextIds(새 칸) | 선후행(precedes) |
| Work.topics(새 칸) | 주제 항목(topic) + 관련(relates_to) |
| User | 사람 항목(person, 사번 = empNo) |
| owners·ownerHistory | 수행(performs) + 기간, 담당 시작·종료 이력 |
| User.dept·Work.dept | 조직 항목(org) + 소속(belongs_to) |
| Work.partners·agency | 조직 항목 + 참조 |
| Doc | 산출물 항목(artifact, 하위 유형 = 문서 유형) + 산출(produces) |
| Action(미완료) | 할 일 업무(work, 속성 마감) + 담당(performs) + 포함 |
| Decision·TEvent | 이력(지도 항목 아님). 카드에서 근거 문단으로 연결 |
| cautions·current(담당자 작성) | 메모 이력(유의·진행 중) |
| Handover(확정) | 인계 이력 + 담당 선 「전임 → 후임」 |
| mapHidden(새 칸) | 숨김 |

- **D24-3 확장 3단계.**
  - ① 업무 지도: 업무 상세의 「지도」 탭. 그 업무를 중심으로 그린다.
  - ② 내 지도: 메뉴 「업무 유니버스」. 내가 담당하는 업무 전체를 그린다.
  - ③ 팀·부서 지도: 같은 메뉴에서 범위를 바꿔 본다. 부서·팀 단위로 접고 펼친다(유니버스 묶기 = refs). 위험 점검을 함께 보여 준다. 「전체 보기」 사용자만 볼 수 있다.
  - ①·②에서는 업무잇다의 열람 범위(본인 담당 + 인수 대기)를 그대로 지킨다.
- **D24-4 「전체 보기」 사용자.** User.role = 'lead'(팀장 역할, 시연용 가상 인물)는 자기 부서의 모든 업무를 본다. 다른 화면도 같은 범위로 본다.
- **D24-5 지도 편집(1차).** 아래 동작은 모두 AppState 명령이다. 변경 이력에 기록하고 version을 1 올린다.
  - 담당 넘기기·추가: owners·ownerHistory
  - 업무 연결: 상위(parentId)·관련(relatedIds)·선후행(nextIds)
  - 메모: Stmt를 담당자 작성으로 cautions(이슈·주의) 또는 current(진행 중)에 넣음
  - 주제 붙이기: topics
  - 업무 추가: 업무잇다 업무 등록 창을 엶
  - 숨김: mapHidden
  - 삭제는 업무잇다 화면에서만 한다(되돌리기·이력은 업무잇다 방식).
- **D24-6 개선(1차).**
  - a. 지도 카드의 결정·조치 → 근거 문서 문단으로 이동
  - b. 인계 확정이 지도에 「전임 → 후임」으로 보임 + 스냅샷 지도와 지금 지도를 나란히 보기
  - c. 지도 위험 점검을 대시보드 「AI가 발견한 누락·갱신 필요 항목」과 같은 목록으로 합침
  - d. 시점 되감기(날짜 → 그 시점 지도)는 여유가 있으면 한다.
- **D24-7 합쳐 불러오기.** 업무잇다 백업 파일을 내 데이터에 **더한다**(지금의 「바꿔 불러오기」도 남김).
  - 사람은 사번(empNo)으로 맞추고, 없으면 이름+부서로 맞춘 뒤 미리 보기에서 확인한다.
  - 업무는 정규화한 이름이 같으면 같은 업무 후보로 보고, 미리 보기에서 사용자가 정한다. 겹치는 ID는 새로 매긴다.
  - 문서는 제목+작성일로 맞춘다.
  - 맞추는 판정은 유니버스 merge 규칙을 쓴다.
- **D24-8 스키마 7.** AppState.schema 6 → 7. 새 칸과 이전 데이터 변환:

| 위치 | 새 칸 | 이전 데이터(6)를 7로 바꿀 때 |
|---|---|---|
| User | empNo, role | 비어 있음 |
| Work | nextIds, topics | 빈 배열 |
| AppState | mapHidden | 빈 배열 |

## 4. AI와 규칙

- **D24-9 키 방식.** 유니버스 llm(공식 SDK 묶음, `api.anthropic.com`만 호출)을 쓴다.
  - 키는 이 브라우저 저장소에만 둔다. 데이터 옮기기·백업에는 넣지 않는다.
  - claude.ai 게시 방식(window.claude)과 Claude|Mock 토글은 뺀다. 대신 설정에 「AI: 키 있음/없음」을 표시한다.
- **D24-10 AI가 하는 일:**
  - ① 문서 분석·반영 제안(결정·일정·조치·개요 + 담당자·조직·주제 = 지도 재료)
  - ② AI 업무 검색
  - ③ 지도 요약 문장(근거 칩)
  - 셋 다 유니버스 검증을 거친다: 인용이 원문에 있는가, 근거 ID가 실제로 있는가, 짧은 인용 규칙·표 순서 맞추기를 지키는가. 꼼꼼히 읽기(두 번째 대조 호출)와 지도 정보 블록도 쓴다.
  - 검증에 실패한 항목은 「추가 확인 필요」로 낮춘다(업무잇다 원칙과 같음).
- **D24-11 키가 없을 때(규칙).**
  - 담당자·할 일·마감·표·PDF 복사 글 정리·메모·비슷한 이름: 유니버스 doc-attach·text-extract 규칙
  - 결정·일정·개요: 업무잇다 Mock 규칙
  - 위험 점검·근거 찾기: 유니버스 insight 규칙
  - 시연 데이터의 지도 요약 문장은 사전 생성으로 받아 둔다(받기 전에는 규칙 문장).

## 5. 시연 데이터·제출물
