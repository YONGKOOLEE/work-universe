## 3. 빌드 방식 (P-1)

- 소스: `app/src`의 ES 모듈(`import`/`export`). Node 단위 테스트가 그대로 불러온다.
- 빌드: `npm run build` → esbuild `format: iife` → `dist/app.js`(모듈 없는 단일 스크립트, 약 442KB, 최소화) + `dist/index.html`(일반 `<script src="app.js">`).
- 빌드 스크립트가 결과물에 `type="module"`, `import`/`export` 문, `fetch(` 호출이 없는지 검사하고, 있으면 실패한다.
- 샘플 데이터는 JS 모듈로 감싸 번들에 포함한다(12.1).
- 대안 K-3(인라인 단일 HTML)은 쓰지 않았다. 스크립트 파일 분리 방식으로 P-1이 통과했기 때문이다.

## 8. T-05 탐색 화면 (2026-10-01)

- 구조: 상세 내용은 `view/describe.js`(순수 함수, Node 테스트)가 만들고, `ui/detail.js`가 그리기만 한다. 그래프는 `ui/graph.js`(Cytoscape.js)가 `view`를 받아 그린다.
- 화면: 그래프 + 오른쪽 상세 패널(속성, 연결된 노드와 담당 기간, 이력), 그래프 아래 범례, "전체 보기" 버튼. 노드를 고르면 이웃만 또렷하게 보이고, 빈 곳을 누르면 유니버스 개요로 돌아온다.
- 참조한 유니버스의 노드는 점선 테두리, 동일성 연결로 합쳐진 노드는 이중 테두리로 구분한다(02-design 2절). 실제 표시는 T-10에서 확인한다.
- 이력 목록(R-14 대체 수단)은 상세 패널에 이미 들어 있다. 시간 슬라이더는 T-11이다.
- 화면 점검 중 발견해 고친 것: ① 범례가 그래프를 가려 그래프 밖(아래)으로 옮김 ② 노드 추가 뒤 배치를 다시 계산하면 그래프가 화면 밖으로 밀려 새 노드가 안 보임 → 새 노드가 생기면 전체가 보이게 맞춤 ③ 라벨·관계 이름 겹침을 줄이도록 배치 간격 조정.

## 16. T-08 유사 경험자 (2026-10-01)

- 구현: `app/src/rules/insight.js`(순수 함수, view 입력), `app/src/ui/insight.js`(화면). 업무 노드의 「유사 경험자」 버튼 또는 개요의 「유사 경험자 찾기」. 인수인계 초안의 「유사 경험자」 항목에도 같은 결과가 들어간다(받는 사람은 뺌).
- 규칙(D-08에 수치가 없어 정한 부분): 점수 = 같은 주제 3 + 같은 산출물 유형(하위 유형 이름) 2 + 라벨 같은 낱말 1(2자 이상, "업무·관리·처리·확인" 제외). 주제 또는 산출물 유형을 공유하는 다른 업무만 후보이고, 낱말은 점수에만 더한다. 점수가 같으면 이름순. 같은 업무를 여러 기간 맡아도 한 번만 센다.
- "같은 주제": 유니버스 사이에 사람이 확인해 이은 주제(동일성 연결)는 같은 노드로 본다. 연결이 없어도 **이름이 같은 주제**는 후보로 보되, 화면에 "이름이 같은 주제, 연결 확인 전"이라고 밝힌다(연결을 확정하라는 신호, T-10 확인 목록과 이어짐).
- "현재 담당자": 기준일에 기간 안에 있는 수행 연결의 사람. 기준일은 화면에서 오늘 날짜. 기준 업무의 **과거** 담당자(예: 한가람)는 "다른 업무"를 맡은 적이 없으면 나오지 않는다(D-08은 다른 업무만 비교). 그 사람은 인수인계 초안의 "관계자"로 나온다.
- 결과 상태: `ok`(사람 목록), `none`(비교는 했지만 비슷한 업무를 한 사람이 없음), `insufficient`(기준 업무에 주제·산출물 연결이 없음 = 데이터 부족, R-05 ②).
- 샘플 추가(T-13에서 당겨 옴): 사례 2 `app/data/sample-event.js`(U-B 가상행사팀: 업무 4, 사람 2, 주제 2, 윤바다는 2025 행사 담당), 부서 `app/data/sample-dept.js`(U-D1 가상 운영부: 결제운영팀 + 행사팀, 윤바다 사번 자동 연결). 부서 → 팀 → 업무의 여러 단계 묶기도 이 샘플로 시연한다.
- 정답 표(`answers-v1.js` SE-1~3): 부서 화면에서 "대사 확인"의 유사 경험자는 운영 담당·윤바다·정산 담당(모두 3점). 앞의 두 역할은 결제운영팀에서 사람이 이은 "대사" 주제의 카드승인 업무 담당자이고, 윤바다는 이름이 같은 주제의 2025 행사 담당자. 처음 정답 표(윤바다만)는 샘플의 주제 연결을 놓친 것이었고, 결과를 확인한 뒤 고쳤다.
- 합쳐진 사람(윤바다)은 한쪽 유니버스의 노드만 숨기면 남고, 모든 노드를 숨겨야 후보에서 빠진다.

## 17. 사용자 화면 확인: "정신없어 보임" 원인과 수정 (2026-10-01)

사용자가 부서 유니버스(U-D1)를 보고 정신없다고 했고, 데이터에 익숙하지 않은 탓인지 원인을 물었다. 캡처로 확인한 결과 화면의 문제였다.

| # | 원인 | 수정 |
|---|---|---|
| 1 | 접힌 팀 꼭지에 가려진 개수(＋N)가 팀 자신의 노드만 세어, 그 아래 하위 유니버스가 있는 팀(결제운영팀)은 숫자가 없어 무엇이 접혀 있는지 알 수 없었음 | 그 아래 하위 유니버스의 노드까지 센다(결제운영팀 ＋46). 테스트 추가 |
| 2 | 부서처럼 전부 참조한 노드면 모든 노드에 점선 테두리(참조 표시)가 둘려 어수선함 | 점선은 내 노드와 참조 노드가 섞여 있을 때만 |
| 3 | 연결 이름(수행·포함 등)이 모든 선에 붙어 노드가 많으면 글자가 빽빽함 | 연결 14개 이하일 때만 모두 표시, 그보다 많으면 고르거나 마우스를 올린 노드의 연결에서만 |
| 4 | 개요 "노드 57개"와 화면의 9개가 어긋남 | "지금 화면 9개 · 접힌 것까지 전체 57개" |

- 아직 남은 것: 28개 이상을 한꺼번에 펼치면 글자가 작아진다(맞춤 확대 때문). 유니버스마다 색을 달리하는 방안 등은 사용자 의견을 받아 정한다.

## 18. CR-6: 인수인계 초안 보강 (2026-10-01)

- 배경: 사용자가 초안이 "알맹이 없이 이력만 나열한 것 같다"고 했다. 원인은 ① 월말 정산 데이터에 업무 내용(절차·주의사항·마감·진행 중인 일·연락처)이 거의 없었고(노드 설명과 메모 합계 246자, 메모 1건) ② 설계 D-09의 8개 항목이 업무의 구조와 이력만 다뤘으며 ③ 규칙 기반은 기록을 옮겨 적는 것까지만 하기 때문이다(LLM도 데이터에 없는 내용은 만들 수 없다).
- 변경(승인: "둘 다 진행해"): 02-design 5.6·D-09·12.2 메모 payload. 상세는 5.6 표.
  - 초안 항목 8 → 10개: 업무 개요 / 세부 업무·절차(진행 순서 + 절차·사용 시스템) / 일정·마감 / 주의사항·노하우 / 진행 중인 일 / 산출물·문서 위치 / 관계자·연락처(문의: 보내는 사람) / 최근 이슈 / 이전 인수인계 / 유사 경험자. 선후행은 세부 업무·절차에 합침.
  - 데이터 틀은 그대로. 업무 속성 약속(절차, 사용 시스템, 주기, 마감, 주의사항 / 산출물: 위치 / 사람: 연락처)과 메모 범주(`payload.category`: issue·caution·in_progress·resolved, 없으면 issue). 메모 입력 양식에 「분류」 선택을 추가.
  - 진행 중인 일은 같은 대상에 이후 "해결됨" 메모가 있으면 뺀다. 최근 이슈는 이슈 범주만. 메모는 범위 업무가 속한 유니버스의 것만 쓴다.
- 데이터: 월말 정산(U-A1)에 업무별 절차·사용 시스템·마감·주의사항, 문서 위치, 연락처(내선, 가상), 메모 7건(이슈·주의사항·진행 중·해결됨)을 채움(원래 T-13 범위의 일부). 글 분량 246자 → 약 500자 이상.
- 판단한 것: 보내는 사람은 관계자에서는 빼지만(5.6 기존 규칙) 연락처가 있으면 "문의: 보내는 사람"으로 맨 앞에 둔다. 받는 사람이 가장 먼저 필요한 정보라고 보았다.
- 한계: 규칙 기반이라 문장이 "속성 값을 이어 붙인 것"이다(예: 절차가 한 줄에 ①②③). 이를 읽기 좋게 풀어 쓰는 일은 LLM(T-12, 사전 생성)의 몫이며, 그때도 데이터 범위 안에서만 쓴다. 다른 유니버스(카드승인 등)의 속성·메모는 아직 비어 있어 그 초안은 여전히 얇다(T-13에서 채움).
- 검증: 단위 테스트 147개, Chrome·Edge 점검(새 항목이 화면에 보이는지 포함).
