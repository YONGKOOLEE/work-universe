## 3. 빌드 방식 (P-1)

> 2026-10-01 11절 "HTML 파일 하나"로 대체됨. 아래는 처음 방식의 기록이다.

- 소스: `app/src`의 ES 모듈(`import`/`export`). Node 단위 테스트가 그대로 불러온다.
- 빌드: `npm run build` → esbuild `format: iife` → `dist/app.js`(모듈 없는 단일 스크립트, 약 442KB, 최소화) + `dist/index.html`(일반 `<script src="app.js">`).
- 빌드 스크립트가 결과물에 `type="module"`, `import`/`export` 문, `fetch(` 호출이 없는지 검사하고, 있으면 실패한다.
- 샘플 데이터는 JS 모듈로 감싸 번들에 포함한다(12.1).
- 대안 K-3(인라인 단일 HTML)은 쓰지 않았다. 스크립트 파일 분리 방식으로 P-1이 통과했기 때문이다.

## 8. T-05 탐색 화면 (2026-10-01)

- 구조: 상세 내용은 `view/describe.js`(순수 함수, Node 테스트)가 만들고, `ui/detail.js`가 그리기만 한다. 그래프는 `ui/graph.js`(Cytoscape.js)가 `view`를 받아 그린다.
- 화면: 그래프 + 오른쪽 상세 패널(속성, 연결된 노드와 담당 기간, 이력), 그래프 아래 범례, "전체 보기" 버튼. 노드를 고르면 이웃만 또렷하게 보이고, 빈 곳을 누르면 유니버스 개요로 돌아온다.

## 23. T-11(일부) 밀집/공백 인사이트 (2026-10-02)

- 구현: `rules/insight.js`의 `densityGaps(view, {asOf, n})`(순수 함수), 화면은 인사이트의 세 번째 탭 「밀집·공백」. 정답 표 `answers-v1.js`의 `density_gaps`(DG-A1, DG-B, DG-B-N4).
- 규칙(02-design 5.5를 구체화한 부분):
  - **조직 단위:** 업무 노드가 속한 유니버스. 부서 화면이면 팀·업무 유니버스별로 한 줄씩 나온다. 업무가 없는 꼭지 유니버스(부서·팀 꼭지만 있는 것)는 표에서 뺀다.
  - **활성 업무:** 숨기지 않은 업무. 설계에 "끝난 업무" 표시가 없어서, 공백을 둘로 나눠 보여 주고 판단은 사람에게 맡긴다(R-05 ③): `담당 기록 없음` / `이전 담당자만 있음(마지막 담당자, 종료일)` — 후자는 2025 행사처럼 끝난 업무일 수 있다.
  - **현재 담당:** 기준일(화면은 오늘)에 기간 안에 있는 수행 연결(유사 경험자와 같은 `isCurrent`). 숨긴 사람·연결은 세지 않는다.
  - **상위 업무 공백:** 하위 업무(포함 연결)에 담당자가 있으면 "하위 업무 4개 중 2개에 담당자 있음"을 덧붙인다(카드승인 「승인」). 담당을 물려받는다고 보지는 않는다.
  - **밀집:** 기준일에 한 사람이 서로 다른 업무를 N개 이상 맡음. 여러 유니버스에 걸친 같은 사람(사번 연결)은 합쳐 센다.
  - **데이터 부족:** 보기 전체에 수행 연결이 없으면 결론 없이 "데이터 부족"과 마지막 입력 시점만. 부서 화면에서 한 유니버스만 연결이 없으면 그 줄만 "데이터 부족"으로 표시하고 공백 목록에서 뺀다(연결이 없는 걸 공백으로 단정하지 않음).
- **N 기본값(사용자 결정 대기):** 설계는 "기본값은 데이터로 정한다"고만 했다. 지금 샘플에서 한 사람이 맡은 업무는 최대 3개(도하람)라 임시로 3(`DENSE_DEFAULT_N`)으로 두었다. 화면에서 바로 바꿀 수 있고 상수 하나만 고치면 된다. T-13 데이터가 정해지면 다시 본다.
- 점검 중 발견: 브라우저 점검은 앞 단계에서 서하늘 → 보고 수행 연결을 더하므로 그 시점의 공백은 자료 수집 하나다(점검 기대값을 고침, 화면은 맞았음). 부서 화면에서 좁은 표의 머리글이 한 글자씩 줄바꿈되는 것을 스크린샷으로 발견해 고침.
- 검증: 단위 테스트 190개(그때 기준, `tests/density.test.js` 12개), Chrome·Edge 점검(월말 정산·부서 화면, N 조정, 표 크기), 규모 500노드 1.5ms, 비밀값 0건, R-06 형식 점검 통과.
- 미확인: 03-plan T-11의 "조직개편 전후 이력이 이어져 보임"과 "입력이 중단된 조직관리 유니버스" 오류 검증은 조직관리 유니버스(U-O, T-13)가 있어야 한다.

## 24. 두 번째 전체 검토와 수정 (2026-10-02)

- 계기: 사용자가 사람 상세에서 업무 3개를 보고도 "밀집"을 찾지 못함 — 계산 결과가 사용자가 보는 자리에 없었다. 같은 종류의 문제를 포함해 4범주(화면 발견성, 규칙 정합성, 요구사항 추적·문서, 실행 조건·보안)를 읽기 전용 하위 에이전트로 나눠 검토하고 수정은 본 세션에서 했다. 결과 표는 `docs/review-2026-10-02.md` 6절.
- 화면: 사람 상세 "지금 맡은 업무 N개 — 밀집 기준(N개 이상)에 해당/아래", 업무 상세 "현재 담당: …" 또는 "공백 — …", 업무·주제 상세 "반복 비효율 패턴 N건에 포함", 수행 연결에 현재·종료·예정 표시, 개요·시작 화면에 인사이트 세 종류 안내, 근거 버튼·연결 노드가 접힌 하위 유니버스 안이면 펼쳐서 보여 줌, 초안 대상 업무의 현재 담당 표시와 한 명이면 보내는 사람 미리 고름, 버튼 이름 "인수인계 초안 만들기"로 통일. 밀집 기준 N은 화면에서 바꾸면 세션 동안 사람 상세에도 같이 쓴다(저장 안 함).
- 규칙(해석 포함):
  - 기간 상태는 `view/describe.js`의 `periodStatus` 하나로 판정한다(현재·종료·예정). 시작일이 기준일 뒤면 "시작 예정"으로 표시하고, 유사 경험으로 세지 않는다.
  - 공백 종류에 `scheduled`(시작 예정 담당자만 있음)를 더했다. 업무 상세와 밀집·공백 탭이 같은 함수(`workLoad`)를 쓴다.
  - 업무 노드의 기간(12.2 `period`)이 기준일 전에 끝났으면 활성 업무가 아니다 — 공백·밀집에서 빼고 개수만 알린다. 23절의 "설계에 끝난 업무 표시가 없다"는 해석을 고친다(12.2에 이미 있었음).
  - 수행 연결이 숨긴 업무에만 있으면 "데이터 부족"(이전에는 "없음"이라는 결론을 냈음).
  - 인수인계 초안: 합쳐진 업무의 다른 유니버스 메모도 범위에 든다. "해결됨" 다음 판정은 날짜가 아니라 이력 정렬 순서(같은 날이면 기록 순서, 14절).
- 실행 조건: 처음 열 때 샘플 저장이 실패하면(용량 부족) 빈 화면 대신 메모리의 샘플을 읽기 전용으로 열고 W-STORAGE(install)로 알린다. 본문은 썼는데 목록 쓰기가 실패하면 본문을 되돌린다. 초기화는 목록에 없는 유니버스 키도 지우고, 실패하면 알린다. 용량 초과 판정에 구형 Firefox 이름·코드를 더했다(실제 확인은 못 함). 주소의 깨진 인코딩(#%E0)은 시작 화면으로.
- 검증: 단위 테스트 209개(새 파일 `storage-fail`·`review3`·`work-load`, `density`에 personLoad 2개), Chrome·Edge 점검(사람·업무 상세 한 줄, 현재·종료 표시, 반복 비효율 한 줄, 접힌 유니버스 펼치기, 초안 미리 고름, 밀집·공백 데이터 부족, 밀집 근거 버튼). 점검 중 발견: 「승인취소」는 최상위 업무라 접혀 있어도 위로 드러나는 노드여서 펼치기 점검 대상을 하위 단계 업무 「요청 검증」으로 바꿈.
- 남은 것: 결정 목록(review 6.3), 도하람의 담당 시작 이벤트 부족(T-13 데이터 정리 때).
