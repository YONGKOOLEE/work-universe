## AI 활용

**개발 과정.** 설계·구현·검증 전 과정을 Claude Code로 진행했습니다. 계획 문서(착수·요구사항·설계·계획)를 먼저 사람이 승인하고, 그 기준으로 작업을 하나씩 구현·검증했습니다. 저장소 기록으로 확인되는 결과는 단위 테스트 〔2010개 이상〕, 로컬 커밋 〔2026-10-25 이른 기록 152건〕, 전체 검토 12회와 그 뒤 기능별 나란히 재검증입니다(수치는 제출 압축 때 다시 셈). 검토마다 하위 에이전트가 화면·코드·문서를 나눠 읽었고, 확인된 결함은 고친 뒤 수정 전 판과 나란히 돌려 다시 검증했습니다. 사용성은 "처음 보는 사용자" 역할의 에이전트 점검(기록 문서에 1·2·3·5회차, 개편 뒤 6회차는 docs/review-2026-10-26.md 4절)과 일상 사용 점검 2회차로 확인했고, **이는 에이전트의 역할 수행이며 실제 사람 관찰이 아닙니다.**

**제품 안에서의 AI 역할.** 판단의 중심은 규칙입니다. 규칙이 이력에서 근거를 찾고, AI는 **문장을 쓰거나 후보를 제안**할 뿐입니다. 키가 없어도 모든 기능이 동작합니다.

| | 어디서 | AI가 하는 일 | 앱이 확인하는 것 | 사람이 하는 일 |
|---|---|---|---|---|
| 가 | 「인수인계」 공간의 인수인계 초안·「매주 점검」 공간의 인사이트 설명 | 규칙이 고른 근거만 보고 문장을 다듬음(키 없으면 개발 중 미리 받아 둔 「사전 생성」 문장) | 근거 ID가 실제로 있는지, 근거 내용의 지문이 같은지, 원문 인용이 근거 글에 있는지. 안 맞으면 원래 문장 유지(「원래 문장을 유지함」) | 초안을 확인하고 확정 |
| 나 | 업무정의서 「AI로 변환」(「지도 관리」 → 「가져오기·내보내기」) | 규칙 변환이 못 나누는 여러 업무 문서를 읽어 지도 초벌 | 항목마다 원문 인용(8자 이상)이 원문에 있는지. 없으면 버리고 「뺀 항목 n개」 표시 | 미리 보기를 확인하고 가져오기 |
| 다 | 팀·부서 묶기의 「AI로 연관 찾기」(「지도 관리」의 「통합 확인 목록」) | 이름이 달라도 뜻이 같은 업무 쌍을 후보로 제안(이유·인용) | 인용 검증. 후보일 뿐 자동으로 합치지 않음 | 「같은 업무」/「다른 업무」 판정 |
| 라 | 「지도 관리」 → 「글로 추가」의 「Claude로 읽기」(CR-19, 기본은 키 없이 「읽어 보기」) | 붙여 넣은 몇 문장에서 항목·연결을 구조화 출력으로 제안 | 아래 「글로 추가」 문단 | 미리 보기에서 체크·고쳐 저장 |

**지어내기를 막는 검증.** AI가 그럴듯한 말을 지어내는 것이 업무 도구의 가장 큰 위험이라, 모델의 답을 그대로 쓰지 않고 앱이 거릅니다: ① 응답은 정해진 JSON 스키마만 받음 ② 근거 ID·지문 확인 ③ **원문 인용(quote)이 원문에 실제로 들어 있는지 앱이 직접 찾아봄**. 통과하지 못한 항목은 버리고 몇 개를 뺐는지 화면에 보입니다. 문장 밑 근거 칩을 누르면 원래 기록 한 줄이 펼쳐져 사용자가 눈으로 확인할 수 있습니다. 인용 검증이 보증하는 것은 "그 구절이 원문에 있다"까지이고, 같은 업무인지·요약이 맞는지는 사람이 판단합니다.

**글로 추가(CR-19)의 AI 경로와 한계.** 「글로 추가」는 몇 문장의 글에서 사람·업무·산출물과 연결을 **원문 구절과 함께 미리 보기**로 제안하고, 사람이 체크한 것만 한 번의 기록으로 넣습니다. 기본은 키 없이 도는 **규칙 읽기**이고, 키가 있으면 「Claude로 읽기」가 더해집니다.
- 보내는 것: 붙여 넣은 글과 지금 지도의 항목 이름·유형 목록뿐입니다(「키와 데이터」 도움말에 같은 말).
- 검증(원문 구절): 항목과 연결마다 모델이 낸 구절이 글에 **글자 그대로 있어야 하고(4자 이상, 글 전체를 베낀 긴 구절은 불가)**, 항목 이름이 글에 낱말로 있어야 하며, 사번은 글에서 그 이름 바로 뒤 괄호에 있을 때만 쓰고, 연결은 구절 안에 두 끝 이름이 모두 있고 관계가 두 유형에 맞아야 합니다. 어긋나면 그 행만 버리고 개수를 알립니다.
- 검증(문장 가드): 구절이 든 문장에 규칙과 같은 가드(부정·지난 일·예정·조건·전언·물음 등)가 걸리면 그 연결은 「확인 필요」로 **처음부터 체크하지 않습니다.** 읽지 못한 문장이 있으면 앞뒤 맥락이 뜻을 바꿀 수 있다고 알립니다. 이 가드는 나란히 재검증(CR-19 R19)에서 Claude 경로가 부정문의 연결을 그대로 통과시키던 결함을 찾아(가짜 응답으로 재현) 고치며 더한 것입니다.
- 처음에는 아무것도 체크하지 않는 이유: 재검증에서 새 줄글을 넣을 때마다 맥락 함정(앞 문장을 뒤집는 문장)이 체크된 채 나오는 것이 발견되어, 미리 정한 멈춤 규칙대로 기본을 "체크 없음"으로 바꿨습니다. 이 선택은 2026-10-25 사용자 승인("지금 그대로 승인")으로 확정됐습니다(decisions-pending C19-9).
- **한계(정직하게):** (1) Claude 경로는 **가짜 응답으로만** 검증했고 실제 호출은 확인하지 못했습니다. 실제 모델이 표 기호를 떼거나 글을 바꿔 인용하면 그 행이 검증에서 버려져 결과가 줄 수 있습니다. (2) 규칙 읽기는 정해진 모양의 현재형 문장만 읽어 놓치는 문장이 많습니다(놓치는 것은 괜찮고 잘못 읽는 것은 안 된다는 선택). 줄글 회귀 묶음(86·155·173·140·79문장)은 재검증에서 잘못 읽은 문장을 모아 규칙을 고친 것이라 실제 사용자 글 전반의 정확도를 보증하지 않습니다. (3) 사람이 미리 보기를 확인하는 단계가 안전장치의 마지막 층이며, 확인 없이 자동 저장하지 않습니다.

**키 없이도 동작.** 규칙이 근거를 찾고, 문장은 개발 중 Claude에 넣어 미리 받아 둔 문장(「사전 생성」, 생성일 2026-10-24, 예시 지도 한정)입니다. 앱은 열 때마다 근거 ID와 지문을 검증해 맞지 않으면 규칙 기반 문장으로 바꿉니다(사전 생성 문장 지문 41줄 일치를 점검). 이력이 없는 항목은 지어내지 않고 「이력 부족」이라고 표시합니다. 화면에는 문장이 「사전 생성」·「규칙 기반」·「Claude API」 중 무엇인지 표시됩니다.

**키와 보안.** 제출물에는 키가 없습니다. 심사자가 쓰려면 설정에서 본인 키를 넣고, 키는 이 브라우저 저장소에 암호화 없이 저장되며 내보낸 파일·폴더·이력에는 들어가지 않습니다. 호출은 api.anthropic.com 한 곳으로만 갑니다. file://로 연 같은 브라우저(Chrome·Edge)의 다른 로컬 HTML도 이 저장소를 읽을 수 있으니, 쓰지 않을 때는 「키 지우기」를 누르고 짧은 기간만 쓰는 키를 권합니다(브라우저별 실제 범위는 미확인). 키가 없으면 기록을 어디로도 보내지 않습니다. 브라우저에서 키를 직접 쓰는 방식은 공식 문서가 내부 도구·신뢰된 사용자·시연 용도에 한해 쓰라고 경고하는 방식이어서, 조직 서비스로 가면 서버 중계로 바꿔야 합니다.

**다음 단계.** 사내 LLM을 꽂는 공급자 자리는 있고 비어 있습니다. 연결해도 인용 검증과 규칙 기반 대체는 그대로 적용됩니다. 실데이터를 쓰려면 사내 보안 검토가 먼저 필요합니다(전환 경로 문서 참고).

| 단계 | AI가 하는 일 | 사람이 하는 일 |
|---|---|---|
| 개발 | Claude Code가 설계 초안·구현·테스트·결함 검토 | 계획 승인, 결과 확인 |
| 문장 준비 | Claude가 근거 목록을 읽고 문장 작성(개발 중, 사전 생성) | 문장 검토 |
| 실행 중(키 없음) | 규칙이 근거 검색, 앱이 근거 ID 검증, 불일치는 규칙 기반 대체 | 초안 확인·확정, 인사이트 해석 |
| 실행 중(키 있음) | 문장 다듬기·AI 변환·연관 후보·글 읽기 제안 | 모든 제안의 확인·확정·체크 |
| 이력 없음 | 「이력 부족」·「데이터 부족」 표시 | 입력 보강 |
